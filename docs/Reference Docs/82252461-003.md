Introduction

         The ClearPath Extension Kit for OS 2200 provides an additional software execution
         environment for OS 2200 systems. This execution environment allows many
         applications developed originally for UNIX and Linux execution environments to run
         mostly unmodified in the highly secure OS 2200 environment. Refer to the ClearPath
         OS 2200 Software ClearPath Extension Kit for OS 2200 Conceptual Guide (8225
         2495) for an understanding of the components and communications involved in
         providing this environment.

         This guide describes how to use the provided OS 2200 Native Control Programs
         (ONCPs) to execute Native Extension processes, including developing new
         applications using language and scripting processors, such as Python®, Java™, and
         bash, and executing existing utilities and applications imported from open source
         repositories. Refer to the ClearPath OS 2200 Software ClearPath Extension Kit for
         OS 2200 Installation and Administration Guide (8225 2446) for a description of how to
         download and install additional open source applications for use in the Native
         Extension environment.

Programs

         The ClearPath Extension Kit for OS 2200 provides application programming interfaces
         (APIs) for interacting with Extension Kit processes (see Section 4) and OS 2200 Native
         Control Programs (ONCPs) that use the APIs for commonly used program
         development applications. Each issuing ONCP triggers creation of a process in the
         Extension Kit execution environment, and sets up communication paths that allow
         input and output flow between the new process and the ONCP.

         This section describes how to invoke and use the supplied ONCPs. In addition, cursory
         command usage descriptions are provided for open source applications included with
         this product, but for which ONCP processor calls are not provided. For information on
         the behavior of specific ONCPs, see Section 5.


2.1. OS 2200 Native Control Programs
         For several of the most common programming languages and utilities provided with
         this product, ONCPs are also provided to allow direct execution in demand runs,
         runstreams, and addstreams. These ONCPs are based on commonly used open
         source and software development tools available in UNIX and Linux based systems.
         Additional details are provided in the following sections.

2.1.1.   ONCP Command Format
         The provided ONCPs must be called using unformatted ECL. The format is

         @'<ONCP>[,D] [oncp-options] [input-parameter-1 [input-parameter-2 … ]]

         where the provided <ONCP> values are

            BASH
            GIT
            GREP
            JAVA
            JAVAC
            NX
            PYTHON



8225 2461–003                                                                               2–1
Using OS 2200 Native Control Programs




           PYTHON3
           SVN
        Additional ONCPs can be built using the provided tools described in section 4.

        The processor call option D enables additional logging using each provided ONCP. For
        each invocation of the ONCP, the log messages are written to a separate file whose
        name has the form /tmp/<userid>/<oncp-name>.log.

        The allowed oncp-option values for each ONCP are described in section 5. In
        general, each of these are given as a series of letters or numbers, each preceded by a
        “-“ or “--“. Multiple oncp-option values are separated by spaces.

        The allowed input parameters are text strings, separated by spaces, usually signifying
        input or output file names or ONCP-specific keywords describing operation modes.
        Depending on the specific ONCP, multiple strings may need to be enclosed in single or
        double quotes to insure that all the input parameters are communicated to the newly
        created process.

        When the input parameters are file names, each appears in the syntax of an absolute
        or relative path name. A path name is a series of alphanumeric directory or file names,
        separated by forward slash characters (“/”) indicating the location of the file in the file
        hierarchy provided by CIFS.

        Absolute path names start with a single slash, and provide the entire file location
        specification. Relative path names do not start with a slash, and implicitly start with
        the Current Working Directory (CWD). Before executing the ONCP command, the
        CWD can be set using the cd or chdir command in the CIFS utility (@CIFSUT). If not
        explicitly set, the CWD defaults to the project-id (/os2200/<project-id>/).

        Successive invocations of ONCPs each restart with the CWD established by the CIFS
        utility, regardless of any current directory changes made within the Native Extension
        process launched by an ONCP.

        ONCP Usage Modes
        Several of the ONCPs have multiple usage modes that affect what options are
        accepted and how the input parameters are specified. There are three general usage
        modes for ONCPs: immediate execution, script execution, and interactive execution.
        The general rules for these three modes are described in the following sections.

        Immediate Execution
        In immediate execution mode, the ONCP control statement specifies a single
        execution of a single program in the Native Extension environment. Some ONCPs do
        not support script or interactive modes, therefore, immediate execution is the only
        mode available. The supplied ONCPs that support only immediate execution include
        @'GREP and @'SVN.

         The oncp-options you provide are passed to the executing ONCP as they would be
         if provided when operating on a Linux system. Thus, using the oncp-option: –c in
         the command @'GREP –c xyz *.py will search all the Python source files in the
         current directory for the string xyz, but only prints the number of instances of the
         string xyz in each file, rather than the entire matching lines.

         The @'NX command supports immediate execution of programs (both programs
         provided by this product, and user-provided programs) in the Native Extension
         environment for which dedicated processor call lines are not available. The @'NX
         command can also be used to invoke script or interactive execution modes for
         programs that support these usages, but for which individual processor calls are not
         available.

         It is also possible to implement site-specific ONCPs to avoid the need to use the @'NX
         command by using the interfaces provided with the ClearPath Extension Kit. See
         section 4 for details.

         Script Execution
         In script execution mode, the ONCP control statement specifies a script source file,
         rather than a program to execute. This is supported only by ONCPs that support
         source scripting, including @'BASH and @'PYTHON.

         The oncp-options you provide are passed to the scripting program as command
         options, as they would be used in a Linux command execution. Thus, the –c option (to
         read an entire command line as the main input parameter) and the –x option (echo
         input lines) are valid options to the @'BASH command. Similarly, the –Walways option
         can be used to enable all warning messages when using the @'PYTHON command.

         Interactive Execution
         Some ONCPs, including @BASH and @PYTHON support interactive execution mode. In
         this mode, the input-parameter need not be provided. Each ONCP itself issues
         prompts, accepts subcommands in its supported language, and issues standard
         output and error messages resulting from the execution of each subcommand.

         In this mode, oncp-options are still allowed, such as the –x option for echoing
         subcommand lines during @'bash execution.

         When used in a runstream or addstream, ONCP subcommands can be supplied to
         ONCPs operating in interactive mode as normal batch input lines.

         Since ONCPs trigger execution of widely used open source applications, Unisys does
         not provide complete documentation for their usage. It is normally provided in the
         form of manual pages, written by the open source developers, and tutorial information
         written by the developers and a wide community of users. Refer to the Linux website
         for more information on manual pages for the most common Linux applications,
         including most of the utilities provided by the ClearPath Extension Kit.

2.2. Differences between OS 2200 and x86-64
     Architectures
        OS 2200 and Linux systems can perform all common computing tasks, such as file
        input and output, accepting interactive or scripted commands, and behaving as
        servers and clients in networks. However, many of the details are different. When
        using the Native Extension environment to execute Linux commands and utilities,
        these differences become apparent.

        This section explains and highlights some of the differences, and provides additional
        resources to allow more effective usage of the ClearPath Extension Kit.

2.2.1. Base System Architecture
        Over time, system designs have evolved greatly to run faster, use virtual memory to
        address large amounts of physical memory, quickly access large permanent storage
        systems, and have extensive support for networked communications. Many
        significant differences between the OS 2200 and x86-64 architectures become visible
        when developing applications and passing data between the environments.



2–4                                                                               8225 2461–003
                                                     Using OS 2200 Native Control Programs




         When programs execute in the OS 2200 system architecture, they generate and
         interpret data files and programs according to that system architecture. When
         programs, such as Python applications, execute in the Native Extension environment,
         they generate and interpret data files and programs according to the x86-64 system
         architecture. Since the binary layouts for most data types (text, integer, floating point,
         etc.) are different between the two systems, any data passed between the two
         systems must undergo conversion operations.

         The modern version of OS 2200 system architecture is described in the ClearPath
         OS 2200 Instruction Processor Programming Reference Manual (3850 7802). Also,
         refer to the Intel x86-64 architecture documentation for details.

         Portable languages, such as Python and Java are said to be high level because they
         hide the differences between system architectures. But older programming
         languages, such as the C language that allow programmers to access the underlying
         system state and instructions can show different behavior for the same program
         when using different systems. Therefore, they are considered low level languages.
         Assembly languages, such as MASM on OS 2200 and gas on Linux, allow direct access
         to the actual instructions implemented for a given processor architecture, and are thus
         the lowest “level” programming languages. They allow the most direct control of the
         processor, but are portable only between processors with the same system
         architecture.

         The following table provides some of the differences between these base system
         architectures.

          Text data format            6-bit Fieldata or 9-bit ASCII   8-bit, 16-bit, or 32-bit Unicode

          Instruction size            Fixed width (36-bits)           Variable byte width
          Register addressability     As fixed memory addresses       Not addressable as memory

          Floating point              36 and 72 bits                  32, 64, and 128 bits

2.2.3. File System and File Naming

             environment because files are the main vehicle for conveying application data within
             and between systems. Binary data types, such as integer, floating point, and
             structures written into files on the OS 2200 will not be readable without a conversion
             step in the Native Extension environment, and vice versa. Even the text files
             conveying ASCII data require conversion because of the different character bit sizes,
             although this is usually handled automatically as part of network data transmission.

             Both of these systems support the existence of files to store and allow writing and
             reading of sequences of related text or binary records. The description is simplified
             from these sources to allow easy comparing and contrasting these storage and

        When changing the CWD within a Native Extension process launched by an ONCP,
        such as the cd, pushd, or popd commands within @bash, the new CWD value will
        continue to be used in subsequent commands within that Native Extension process
        and any child processes it creates. However, the new CWD value will be lost when
        that ONCP’s Native Extension processes exit. The original CWD in effect when the
        ONCP was invoked will be restored.

        Relative path names provide only the directory names needed to navigate the
        hierarchy to the desired file. Thus, if the CWD is currently set to
        /home/<username>/subdir1/subdir2/, then using the relative path name
        subdir3/myfile.txt will be equivalent to specifying the absolute path
        /home/<username>/subdir1/subdir2/subdir3/myfile.txt. Additional
        shortcuts are provided to more conveniently access commonly used relative
        directories.

            The character “.” (period) refers to the CWD. The most common use of this syntax
             is to specify execution of a user program similar to the @bash subcommand.
            The sequence “..” (two periods together) refers to the parent directory. This
             syntax allows a script to refer to files or different subdirectories above the CWD
             in the file hierarchy.
            Multiple consecutive slashes are automatically collapsed to a single slash. This
             syntax allows the CWD specification to end with a slash, while relative path names
             that use it also provide slashes to indicate subdirectories.

        Using these path name syntax facilities, a user or script can employ a relative path
        name to specify any known location within the current file hierarchy without the
        knowledge of the absolute path. For example, if the CWD is currently set to
        /home/<username>/subdir2/subdir3a/ and the subdir2 directory also included
        a subdirectory named subdir3b, then a script executing in subdir3a could refer to a
        file in subdir3b using the relative path name ../subdir3b/knownfile.txt,
        without knowing the name of the parent directory of subdir3a. These syntax
        facilities are used for scripting in the Native Extension environment.

        For files that reside in a location other than the first three levels under /os2200 in the
        CIFS file hierarchy, such as /home/<username>/myfile.txt, the path name cannot

            @PRT MYHOME.MYFILE/TXT

2.2.4. User Identity and File Ownership
         OS 2200 provides a rich collection of user identity management and resource
         ownership facilities. These allow each site to tailor the level of user access and file
         security appropriately. The default Linux execution environment provides a more
         limited selection of such tools, revolving around a numeric user identifier (uid) and
         group identifier (gid), together with a collection of resource access rules using these
         values for one or more user names and fixed resource permissions ("modes"). Refer to
         the Linux website for more information.

         These two identity management and resource protection environments are not
         directly equivalent. Nevertheless, CIFS provides numerical uid and gid values for files
         and associates these values with OS 2200 userids to facilitate normal access and
         usage in the OS 2200 execution environment. Refer to the CIFS for Clearpath
         OS 2200 User, Programmer, and Administrator Reference Manual (7859 6137) for
         additional details.

         In the Native Extension environment, a new Linux uid / gid pair is supplied to the
         process as part of each ONCP startup. These values come from a pool and are
         recycled after each ONCP terminates. They are not maintained across ONCP
         executions. To view the current uid / gid values in an @bash session, issue the
         commands id -u to display the current uid and id -g to display the current gid. If a
         given OS 2200 user activates one or more additional ONCPs while an earlier one is still
         running, each one after the first will be given the same uid / gid values as the first, and
         these values will continue to hold until the last ONCP from that user terminates.

2.2.5. File Permissions
        File permissions can be changed within the Native Extension environment. However,
        there are slight differences when the change takes effect on an OS 2200 system. In
        Linux, changing the mode does not affect any process that already has the file open,
        but does affect all the subsequent open files. In OS 2200, changing the mode does not
        have any effect until the file assign count is zero, even for assignments that occur
        after the mode change but while any run has the file assigned.

2.2.6. Command Structure
        The syntactical structure of commands given in the OS 2200 execution environment is
        called the Executive Control Language (ECL). This is specified and the list of available
        commands and their respective syntax is provided in the Executive Control Language
        (ECL) and FURPUR Reference Manual (7830 7949). Commands are preceded by one
        or two of the “@” character (also called a “masterspace” in the OS 2200
        documentation). Sequences of such commands can be given interactively in demand
        sessions or included in files and executed as runstreams or addstreams as executable
        scripts.

        Similarly, the syntactical structure of commands given in the Native Extension
        environment is called the shell command language. In UNIX or Linux terminology, a
        shell is a utility program, provided as a user interface to the operating system kernel,
        to interpret commands interactively or in executable scripts. The original shell was
        designated sh, and script files written in this language are designated with the file type
        suffix .sh. The primary shell used to support openSUSE Linux and the ClearPath
        Extension Kit is called bash. The bash shell supports both the command syntax
        supported by the original sh shell, and an enhanced syntax with easier programming
        features.

        The @bash ONCP is provided by the Native Extension environment to launch an
        instance of the bash shell from OS 2200. Command usage details for @bash are
        provided in section 5.

2.2.7. Standard Streams
        During execution of OS 2200 runstreams, addstreams, and demand runs, input of
        commands and text data is taken from script files and terminals or network terminal
        emulators. Similarly, in UNIX, Linux, and the Native Extension environment, these
        functions are handled by the standard streams, stdin for input text, stdout for output
        text, and stderr for error or status messages. The term stream, in this context,



2–10                                                                              8225 2461–003
                                                 Using OS 2200 Native Control Programs




         represents a sequence of records, each of variable length that begins when the
         process or session begins, and only ends when the script ends, or an exit command is
         given, or the user logs off.

         During execution of an OS 2200 runstream, addstream, or demand run, input
         commands are echoed and output text data is written to a print file or an output
         terminal. The standard streams behave similarly, and in both cases, controls exist to
         temporarily divert the input or output streams to a different source or destination.

         Because the standard streams are routed through network interfaces as part of ONCP
         execution, the text undergoes character conversion as appropriate. For stdin,
         characters are converted from 6-bit Fieldata or 9-bit ASCII (or whatever alternate
         representation has been configured for a given system) on the OS 2200 side to 8-bit
         Unicode (or whatever alternate LC_* character settings are in effect) on the SAIL side,
         and vice-versa for stdout and stderr. The language settings on both the sides must
         match.

         During execution of ONCPs, the standard streams can be redirected using shell
         operators or programmed I/O operations. The UNIX and Linux program execution
         environments support this concept to allow for easy composition of operations and
         scripts within a single interactive command.

         In the Native Extension environment, the setup for ONCP execution connects stdin to
         the input side of runstreams, addstreams, or terminal emulators as appropriate.
         Similarly, the stdout and stderr streams are connected to the normal OS 2200 stream
         printing facilities, allowing redirection to files with @BRKPT commands. Since there is
         only one output text stream in the OS 2200 execution environment, both stdout and
         stderr streams are combined into a single output stream.

2.2.8. Terminal Emulation
         In a demand run on OS 2200, input typed on an attached terminal or a terminal
         emulator is transmitted via network protocol to the active program to interpret the
         text strings entered. Similarly, output from the system is sent back through the
         network to the terminal. A similar process occurs when Linux systems are accessed
         interactively.

         The different usage histories of OS 2200 systems versus UNIX/Linux systems have
         given rise to different terminal communications protocols being commonly used for
         the two types of systems. Historically, OS 2200 systems use a screen handling
         protocol called UTS (for Universal Terminal System) and block-mode transmission
         protocol called INT1 while UNIX and Linux systems use a screen handling protocol
         derived from early hardwired terminals, such as vt100, vt220 or ANSI, over various
         one-character-at-a-time transmission protocols. Both sets of protocols offer key
         usage features. When a given terminal emulator behavior matches the protocols
         expected by the server, these features work well. However, when the terminal
         emulator screen or transmission protocol has a mismatch with the server’s
         expectation, unexpected behavior is likely.

         A problem arises when an attempt is made to use a character-at-a-time emulator for a
         system that only accepts block mode behavior or vice-versa. When using a UTS

2.2.9. Text File Formats

         compatible with ordinary text files when used inside ONCPs as command or data files.

         recognized by any ClearPath Extension Kit utility programs or ONCPs as command or

         files or elements represented using Fieldata characters to ASCII characters before
         passing them to a Native Extension process launched by an ONCP, and always
         generates ASCII format output.

                files
               A single carriage return (0x0D) – the normal Apple MacOS line terminator

         result in error messages due to the extraneous carriage return character at the end of
         each line.

         compatible with Linux/UNIX based programs by using the w-option of the CIFSUT cp
         and copy commands.

2.2.10. Programming
        Both the historically supported OS 2200 languages, such as the ones supported by the
        Unisys Universal Compiling System (UCS) and many traditional languages used by the
        open source community, use the traditional compile-link-run sequence to prepare
        programs for execution. Refer to the Application Development Programming Guide
        (7831 4077) and the OS 2200 Universal Compiling System (UCS) Conceptual
        Overview (7831 0801) for details on the programming environments supported on the
        OS 2200.

        In the open source community, languages intended for high performance execution,
        such as C, FORTRAN, and C++ use similar steps to generate efficient executable code,
        although the compilers object file formats, and utilities such as debuggers, are all
        different from OS 2200. Open source compilers for the C and C++ languages are
        included with the ClearPath Extension Kit. For open source programming languages,
        the compile and link steps can be combined into a single command, and the
        executable output file can be copied anywhere the proper run-time libraries are
        present.

        For modern languages that emphasize portability and ease-of-use features rather than
        high performance, a translation step from source code into a portable representation
        called a bytecode is performed instead. The bytecode representation is then executed
        directly by a run-time interpreter. Such interpreters include advanced features, such as
        garbage collection and direct interfaces to system features. Both the Java and Python
        programming environments work this way. For Java, the source-to-bytecode
        translation is performed by a separate compilation step, called javac, prior to
        executing the bytecode form. For Python, the Python interpreter handles the
        translation to bytecode automatically as a preliminary execution step.

        In all cases, extensive run-time libraries are needed to support common operations
        that need to interface with the system. For the C language, only a few modest size
        libraries, such as libc are needed. For the C++ language, the libstdc++ library is
        needed as well, and any of dozens of special purpose libraries if extensions or system
        interfaces are used. For both Java and Python, system specific and application specific
        libraries have been developed for use by the open source community.

        There are too many such libraries available to allow them all to be included with the
        ClearPath Extension Kit. However, most widely published libraries are available from
        open source package repositories, such as openSUSE and GitHub, and can be
        downloaded and installed within the Native Extension environment. Refer to the
        ClearPath OS 2200 Software ClearPath Extension Kit for OS 2200 Installation and
        Administration Guide (8225 2446) for instructions on downloading and installing
        additional packages.

2.2.11. Redirecting Input and Output
         Output from programs and scripts can be routed to files for later printing or review.
         On OS 2200, this output redirection and reversion is accomplished using the @BRKPT
         command. Similarly, input redirection can be done with the @ADD command. For more
         information, refer to the Executive Control Language (ECL) and FURPUR Reference
         Manual (7830 7949).

         Within scripts, programs, and interactive commands used within the Native Extension
         environment, redirection of both input and output files is accomplished with the I/O
         redirection system built into the basic I/O system and incorporated into the command
         syntax of command shells, including @bash.

         Briefly, to specify a file as an alternate source of input for a command, use the <
         character (less-than sign), followed by the file name of the desired input file. To
         specify a file as the desired destination for the output of a command, use the >
         character (greater-than sign), followed by the desired file name. Similarly, to redirect
         error messages from a command, use the sequence &> (ampersand followed by
         greater-than sign), followed by the desired output file name. To append to an existing
         file, rather than creating a new file, use the >> sequence (two greater-than signs)
         instead. To pipe the output of one command for use as input to another command on
         the same command line, use the | (vertical bar) character to separate the two
         commands. To efficiently dispose of command output without saving it, send it
         explicitly to the “null” device, using the syntax > /dev/null.

         Once you are familiar with the available commands and these redirection methods, it
         is possible to use these shell syntax elements as a programming tool, especially for
         text file manipulation, both in scripts and interactively. For the redirection capabilities
         of @bash, refer to the GNU documentation and for the special characters usable in
         @bash commands, refer to documentation at https://www.tldp.org.

2.2.12. Signaling to Scripts and Programs
         The normal command to use at the end of shell command session, including @bash, is
         exit.

         Programming language interpreters, such as Python have explicit commands for
         exiting (quit() for Python).

         Due to issues with terminal emulation as described above, single characters that are
         available for exiting, interrupting, or signaling end-of-input, when executing programs
         or scripts in the Linux context, such as ^C (0x03), ^D (0x04), ^X (0x18), ^Q (0x11), ^S
         (0x13), or ^Z (0x1A) may not be effective in the Native Extension environment.

         Therefore, the Native Extension environment provides these supplemental signaling
         methods:

            To signal the ‘end of input’ condition in the stdin stream, use the same sequence
             as when signaling the end-of-input in an ECL runstream: a record containing the
             string @EOF. When running in a demand session, under some terminal emulators,
             entering a control-D followed by a <CR> also works.



8225 2461–003                                                                                    2–15
Using OS 2200 Native Control Programs




           Input commands that begin with an @ (master space) character are immediately
            interpreted as ECL commands and thus cause the current ONCP session to end.
            The only exceptions are the @EOF command, which signals end-of-input, and
            commands that begin with @@ (double master space), which are interpreted as
            transparent ECL commands.
           When working interactively in a demand session, use the command @@X O,
            followed by a <CR> to interrupt a runaway output operation. This may require a
            few seconds to take effect, due to the details of output buffering, but will
            eventually cause the ONCP to discard all remaining output until another input is
            made.
           In a demand session, in some terminal emulators, the sequence control-C
            followed by <CR> will stop the running program and return control within the
            Native Extension environment.
           In a demand session, in some terminal emulators, the sequence control-Z,
            followed by a <CR>, will stop the running program but keep it active as a stopped
            task in the background, while returning terminal input control. You can see all
            stopped jobs by issuing the jobs command. To continue a stopped job, issue the
            command fg <jobnumber>. To permanently kill background jobs, issue the
            command kill -9 $(jobs -p). The jobs will enter the killed state, and be
            removed after entering an additional command.
           In a demand session, to immediately interrupt and stop an ONCP, use the

Operational Considerations

         While the ClearPath Extension Kit for OS 2200 provides support for a large portion of
         the Linux execution environment, not all existing Linux programs and scripts will work
         as expected. Usually, failures are due to the following operational restrictions.


3.1. Use of Privileged Operations
         The Native Extension environment is not the same as a running Linux system. For
         system stability and security, it operates only as a set of containerized, unprivileged
         processes. Programs running in this environment cannot become privileged and have
         no access to system resources that would allow privileged operations. When
         attempting to port existing applications from a direct Linux execution environment,
         such as SUSE or RedHat Linux, built-in attempts to access privileged services will fail.
         To get such applications to work, alternative source coding techniques that do not
         involve use of privileges are needed. Some of these non-functional privileged
         operations are

            SuperUser. User accounts on Linux systems provide a set of permissions that
             allow the user to perform system administrative tasks. User accounts that have
             activated these permissions are called superusers. No user accounts on OS 2200
             systems are equivalent to Linux superuser accounts within the Native Extension
             environment. System administrator privileges on OS 2200 systems are required to
             configure and modify the behavior of Native Extension environment. Therefore,
             traditional Linux shell commands needed to activate privileged behavior, such as
             logging into an account named root, or using the su or sudo commands in bash,
             are not functional in this environment.
            User-specific files. CIFS provides each user with a subdirectory under /home,
             which is visible to other users, but whose contents are by default not accessible
             to any other userid. CIFS also provides a /tmp directory in which any user can
             create, modify, and delete files, but, unlike /home, files in /tmp are visible and
             accessible to other users by default. To prevent other users from accessing or
             deleting your files under /tmp, use the chmod command in @CIFSUT or @BASH to
             control such access.




8225 2461–003                                                                                 3–1
Operational Considerations




           Devices. On systems, the mount and umount commands support mounting and
            unmounting devices and file systems. These commands are not provided in the
            Native Extension environment. CIFS provides the /dev/null, /dev/random,
            /dev/tty, and /dev/urandom devices as a convenience for Native Extension
            processes with their normal semantics. The mount and umount commands may
            be used under CIFSUT with appropriate privileges. Some utilities and programs
            attempt to provide a user prompt, such as a password request by opening
            additional devices under /dev, but this is not currently supported. Examples are
            sftp and ssh.
           The /proc file system. The Linux kernel provides a variety of services to allow
            processes to query and modify system behavior via a synthetic file system under
            the directory /proc. Each time a process references an entry in this directory
            hierarchy, the Linux kernel intercepts the I/O request and satisfies it either via
            synthesizing the requested information (for input requests) or updating a system
            behavior parameter (for output requests). Such requests will only succeed if the
            requesting process has sufficient privilege. In the Native Extension environment,
            CIFS maintains a directory named /proc, and it provides a read-only subset of the
            entries from the SAIL /proc hierarchy. Information about specific Native
            Extension processes can only be accessed by the OS 2200 userid that started
            those processes.
           Shared memory. The Linux kernel provides a set of features to allow processes to
            share pages of virtual memory for communication and performance. Attempting
            to use any of these features in a process running under the Native Extension
            environment will fail.
           Namespaces and control groups. The Native Extension environment is
            implemented using the namespaces and control groups (cgroups) features of the
            SAIL kernel, and thus these features cannot be used within Native Extension
            processes.

        The Linux kernel provides a wide variety of privileged capabilities. These privileged
        capabilities are not available within the Native Extension environment.

        The Native Extension environment runs within a containing SAIL system. However,
        due to the containment, aspects of the SAIL system that require privilege are not
        available within the Native Extension environment.


3.2. Resource Constraints
        Processes running in the Native Extension environment are constrained with respect
        to system resources. Some resource limits pertain to individual active ONCPs, while
        others pertain to the aggregate of all ONCPs running at a specific time. Limits can be
        adjusted by the system administrator. When a resource request exceeds one of these
        limits, the relevant low-level system service call will return a failure status, which will
        sometimes become visible to the user as a failure within the running application,
        depending on the specific programming choices in that specific application.

        Many applications can accommodate such failures without issuing user visible
        notifications. For example, system memory limitations can be overcome by storing
        data in permanent storage more frequently. Others can result in fatal errors at the

         time they occur, and will generally be reflected in specific error messages emitted to
         the stderr stream from the application.

            Number of simultaneously active ONCP sessions – default: 10
            Amount of system CPU usage available to operating ONCPs – default: 100% of 1
             CPU core. ONCPs do not run on the same system CPU core as an OS 2200
             Instruction Processor. Therefore, depending on the system configuration, there
             may be less than 100% of one CPU core actually available for executing Native
             Extension processes.
            Amount of working system memory available – default: 10%
            Number of simultaneously active user tasks (threads) – default: 1000
            Core file size – 0 bytes.

         The per-ONCP invocation resource limitations imposed by the Native Extension
         environment are

            Accumulated CPU time from all tasks running on all cores – default: 86,400
             seconds (1 day)
            Number of independent processes simultaneously active – default: 100
            Amount of working system memory available – default: 1 GiB

         cannot be changed by the system administrator are

            Maximum file size. The normal limits for OS 2200 files are applied by CIFS.

5.1.1.1. Foreground and Background Processes
         Each command issued within @bash, whether interactively or within a script, causes a
         subprocess to be created within which to run the command. This subprocess takes
         over the stdin stream, while the bash process continues to wait for input in the
         background. When the command completes, its subprocess terminates and input
         control returns to bash itself. When the original @bash command exits, by any means,
         all subprocesses also terminate whether they are stopped or still running.

         From within @bash, you can launch a command into a background subprocess directly
         by appending the & character (ampersand) to the end of the command. The @bash
         process will keep control of stdin and you can continue to issue bash commands. If a
         background subprocess requests input, it will stop and wait until it is brought into the
         foreground with a fg command. The jobs command allows you to see the status of
         all background jobs.

         If the terminal emulator supports it, you can also stop a running foreground
         subprocess by issuing the command sequence ^Z <CR>. This sequence returns
         control of the stdin stream of commands to bash itself. This allows you to either kill
         the job or let it to continue with an fg command. To kill it, use the jobs -p command
         to find its process id, then using the kill <pid> command.

         Meanwhile, both bash itself, and any subprocesses running in the background can
         output to the stdout and stderr streams. That output will appear on an interactive
         terminal or a print file, depending on how @bash is invoked.

         Since all subprocesses terminate when the original @bash command exits, trying to
         put a subprocess into the background, by using an & at the end of the @bash
         command itself, will fail. The subprocess will terminate immediately when the @bash
         command exits, before it has a chance to perform any actions.

5.2.2. The ssg.py Module
         OS 2200 provides a powerful stream manipulation processor called Symbolic Stream
         Generator, in the form of the @SSG command. Refer to the Symbolic Stream
         Generator Programming Reference Manual (7831 1784-009) for details. The Symbolic
         Stream Generator accepts its control input in the form of Stream Generation
         Statements (SGSs). Production software builds in the ECL environment often use SGSs
         to specify a variety of related information, such as source and destination files,
         command options, and specific commands. The Native Extension environment
         includes a Python module named ssg.py that provides a parser for SGSs. After
         importing the ssg.py module, you can call the parsing function
         ssg.parse_sgs(<sgs_input_file_spec>). The ssg.parse_sgs() function
         parses the lines in the specified file, and generates an output variable named ssg.sgs
         of type defaultdict(list) that contains the parsed lines as a dictionary of
         keyword,list pairs. Each keyword corresponds to the label used on one or more of
         the SGS input lines, and each list corresponds to the values provided on the remainder
         of the line. Each list may, in turn, be divided into sublists of items separated with
         commas within each field of the SGS input lines.

Error Messages

         The Native Extension components involve significant resource management and
         communication, which may fail in a variety of ways. When a component or message
         fails while executing an ONCP, the ONCP endeavors to provide an error code and
         message showing what failed. This section gives a summary of these messages with
         suggested actions for how to remedy them.

Debugging Output
         When using the D option on any ONCP, the communication across the interface
         between NPCLIB, running in the OS 2200 context, and the NPC Daemon, running in the
         SAIL context, is written into a log file, in addition to triggering their normal behavior.
         The log file is named /tmp/<userid>/<oncp-name>.log, where <userid> reflects
         the user-id that issued the command, and <oncp-name> reflects the name of the
         ONCP that was invoked.

         The messages document the behavior in the ClearPath Extension Kit C programming
         interface (see section 4). The arguments to each call and any resulting output values
         or error codes are logged.

         Additional log files are available to the system administrator to allow configuring and
         diagnosing Native Extension behavior.

Component Availability
         If one of the components providing the Native Extension environment is not
         communicating or has stopped running, then any ONCP command will fail with a
         message indicating that condition. The environment needs to be restarted.

Resource Exhaustion
         When a resource, such as working memory or available processes is exhausted or
         would be exhausted in order to complete a given operation, a message signifying that
         condition will be returned and issued. If this condition is not fatal to the given ONCP,
         such as @bash, then the ONCP will continue to offer services. Otherwise, it will
         terminate. The remedy is to either modify the Native Extension resource constraint
         configuration to provide additional resources, or modify the script or program to
         reduce the resource requirements.

         This section describes the limitation in the OS 2200 Extension Kit.


7.1. Inaccessible CIFS root directories (/bin, /lib,
      /lib64, /run, /sbin)
         The Extension Kit reserves use of the /bin, /lib, /lib64, /run, and /sbin directory names
         at the CIFS root. All files on the OS 2200 and all other CIFS root directories (for
         example, /home and /tmp) are accessible by Extension Kit processes. The /bin, /lib,
         /lib64, /run, and /sbin directories can be created and the files in them can be accessed
         through CIFS, but they are invisible to the Extension Kit. All Extension Kit processes
         are unable to see any of these CIFS directories or files in them.
