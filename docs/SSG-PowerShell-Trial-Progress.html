2b · Area D in detail — how a converted report becomes a real AMT job

Area D is the only area that leaves the self-contained trial and touches a real AMT runtime, so it carries the most vocabulary. These definitions are used consistently throughout this page.

Definition — what the conversion replaces (and what it does not)

This boundary frames every other definition below, so it is worth stating plainly. On OS2200, a report ran as two stages: SSG generated ECL and COBOL card images at runtime, and the generated COBOL then did the actual data processing. SSG never touched customer data — it wrote the program that did.

StageOn OS2200After conversion
1 · Generation SSG symstream reads SGS parameters and emits ECL + COBOL source. replaced — this is the only stage the converter rewrites. The .ps1 body is the generator.
2 · Processing The generated COBOL is compiled (@ACOB), mapped (@MAP) and executed against the data files. unchanged · out of scope — still COBOL, still compiled and run the same way, now invoked as Call-ExternalProgram ACOB / MAP.
This is why every program in §3 reports Call-ExternalProgram calls to ACOB/MAP — those are not stubs or gaps, they are stage 2 being handed off exactly as before. It also sets what “runs clean” means in this trial: the generator produced the right source and reached end-of-job. It does not claim the downstream COBOL was compiled or that any data file was processed — that is the same COBOL as before and is not what we are converting.

Definitions — the two artefacts

TermDefinition
Body
“body-only script”		 The raw SsgConverter output (Examples/Output/<KEY>.ps1). Pure converted SSG generator logic: it calls runtime functions (GetSgsValue, DataLineOrNoStatement, CompareTypeSafe, Process-Skip) but never establishes them. No Set-Jobname, no Initialize, no Connect-Application. Designed to be called, not started — so it cannot be registered as a CC job as-is (MT-008).
Wrapper
“job skeleton”		 The AMT ECL job-control shell around the body. Adds no business logic and duplicates none of the body — it is pure runtime wiring, in four parts: (1) Import-Module AmtPsEclLib/AmtPsSortLib brings the functions into scope; (2) Set-Jobname + Initialize $AmtSettingsFile start the AMT session (ComScript → COM object → real Connect-Application → BatchId/RequestId/joblog); (3) $global:SgsLabels + AddTo-SgsList seed the SGS parameters the body reads — the job CC’s own StartSSG does in production; (4) Trap{ HandleTrapAndAbort } + Fin for error handling and teardown.
Common misconception: wrappers do not handle file input/output. A grep of all 21 AMT172 wrappers for Copy-Item/Move-Item/Out-File/Set-Content and the ECL file primitives (Asg/Qual/Use/Free/Brkpt) returns zero matches — only three path variables. File I/O stays where it always was: inside the generated COBOL. The wrapper is a session, not a file handler.

4 · Converter Fix — Data-Line Parse Bug (T3-001, Area B)

Root cause: COBOL data-division / output lines were emitted by running the whole line through the SSG expression migrator, so ordinary COBOL punctuation was misread as PowerShell operators — hyphens in names (PROGRAM-ID) as subtraction, PIC X(n) parentheses as unbalanced brackets, and level-number digits adjacent to a name (06 FILLER) as invalid tokens.

Before → after (CFH-COPY line 16)

# BEFORE (248 parse errors in the file)
DataLineOrNoStatement ((06 FILLER PIC  X( + ($FILLCTR + ").")))

# AFTER (0 parse errors)
DataLineOrNoStatement ("                     06 FILLER PIC  X(" + ($FILLCTR) + ").  ")

Fix: a new emit path builds each output line as a concatenation of verbatim double-quoted string segments (literal text) and only the [bracketed] references converted with variable context — so [FILLCTR]→$FILLCTR and [INPUT,1,1,1]→GetSgsValue("INPUT,1,1,1") resolve exactly as before. No change to bracket semantics.

Changed: SymstreamProcessor.cs (new OutputLineToPowerShellExpression + quoting helper; both DataLineOrNoStatement emit sites re-routed) and SymstreamExpressionMigrator.cs (made SplitBracketedReferencesAndLiteralParts public). Full write-up: SsgConverter-Fix-20260909.md.
Deployed 2026-09-10: library rebuilt; Build\Console and Build\Gui SsgConverter.dll refreshed (51200 bytes); Examples\Output goldens regenerated. All 5 parse 0; ARCHISEPARE (143) + CFH-COPY (47) run OK.

Reading the converted output — what an “orphaned data line” is

Every converted program carries # Orphaned data line: markers, and they are the most commonly misread thing in the output. They are not comments carried over from the SSG source, and they are not noise.

What it isMeaning
A loss warning A line of SSG output content the converter could not attach to an emit statement — so it preserved the text as a comment rather than silently dropping it. The marker records content that is missing from the generated result.
Not a comment Genuine SSG comments convert separately and are already preserved. An orphaned line is payload that should have been emitted and was not.
Not yet proven harmless Tier-1 “runs clean” measures parse errors and unmocked lookups — neither of which an orphaned line can trip. A program can run clean and still be generating incomplete COBOL.
So they must not be blanket-removed. Deleting them would destroy the only record of what the converter failed to place, and would make the output look cleaner while hiding a real gap. The correct handling is triage: for each marker decide whether the content is genuinely inert (ECL the pass-through already covers) or genuinely lost (belongs in the generated COBOL). If a class of them proves inert and should stop being emitted, that is a converter change in Area B — never a hand-edit of Examples/Output, which is regenerated on every reconvert and would silently revert.
