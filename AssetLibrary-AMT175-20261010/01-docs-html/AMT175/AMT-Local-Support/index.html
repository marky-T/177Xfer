Architecture & data-flow (SSG → PowerShell → AMT + Control Center)

Design/transform time (1→2→3): SSG source — standalone .ssg, embedded in a COBOL program, or part of an ECL job — is converted by the C# tools into a .ps1. Runtime (4→5→6): the host PowerShell runs the script, imports AmtPsEclLib.psm1, which loads the ComScript COM engine, connects to the AMT application, and exposes the service objects the cmdlets call.

Boundary — bands 1–3 happen at transform time; bands 4–6 only work at runtime inside a configured AMT environment (Sys.ini/AmtSettings.xml, ComScript DLL, live AMT app + Control Center). The same .ps1 run in plain PowerShell has no AMT/CC to call.

SSG patterns ↔ AMT library — can the runtime lib run them?

The SSG-ECL Command Matrix resolves patterns P2–P5 at pre-process / compile time (Remove-SsgDirectives.ps1 strips or expands them; the generated C# bakes in the chosen variant). The SSG → PowerShell converter takes the opposite, runtime approach: it emits live .ps1 that calls AMT-library routines, so the SGS-driven behaviour runs dynamically.

Confirmed functions in AmtPsEclLib.psm1: GetSgsValue, Add-Sgs, Xqt, Use, Asg, Free, Qual, Delete, Ers, Erase-File, CompareTypeSafe, SearchConditional, Msg, DataLineOrNoStatement, Skip-Statement, Fin.

Pattern → AMT-lib runtime support

Matrix patternRuns via AMT lib?Function(s)
P5 tokens [PARAM,r,c,f], [*var]✅ Yes — the key oneGetSgsValue("FILE,$I,1,1,…") resolves tokens live (vs. hard-substituted literals in C#)
P3 *INCREMENT / *LOOP✅ Yesnative For (…; -le (GetSgsValue("FILE")); …) — the loop is emitted, not expanded away
P4 *IF / *ELSE / *ENDIF✅ YesIf + CompareTypeSafe / SearchConditional (runtime branch, not compile-time variant)
P1 @XQT / @USE / @ASG / @FREE✅ YesXqt, Use, Asg, Free (+ Qual, Delete/Ers/Erase-File)
P2 *DEFINE / *SET / *PROCESS◑ Partly*SET arithmetic → inline PowerShell expression (converter's expression migrator); no dedicated macro call
P6 #ucob,is / @UCOB,I❌ Noinline COBOL compile directive — a build-time action; nothing in the PS runtime executes it
Takeaway — the AMT PowerShell lib does run the token (P5), loop (P3), conditional (P4) and job/file (P1) patterns dynamically; GetSgsValue is the linchpin (exactly what the generated .ps1 uses, e.g. GetSgsValue("FILE,$I,2,1")). Only inline-compile directives (P6) have no runtime equivalent, and *DEFINE macros (P2) become inline expressions.

Shallow map from function names + the converter's emitted output; internals of each function not traced.

SSG Converter — what it is & how to run it

SSG (Symbiont Stream Generator) source is transformed into PowerShell (.ps1) scripts that run against the AMT PowerShell runtime library.

Logging — a log is written only when /ENABLELOGFILE:TRUE and /LOGFILE: are both supplied. The file log is fixed at Normal verbosity; /VERBOSE affects only console output.

SSG input format

  • Plain-text files, read line by line.
  • Any filename or extension — the input folder is scanned with *.* (convention is .ssg).
  • Top directory only — no subfolder recursion.
  • Must look like SSG — within the first 20 non-empty lines a line must start with * or #; otherwise it is logged Skipped (not SSG).

Output: one .ps1 per input file, with a header and param([string[]]$Parameters).

If sources are OS2200/EBCDIC or fixed-block binary, convert them to plain ASCII text first or the check will skip them.

SSG Converter — known issues

"SymstreamExpressionPrimitive expected."

The conversion fails for a file with an error like:

Error converting <FILE>: SymstreamExpressionPrimitive expected.

Cause: a converter limitation. The parser accepts a leading unary -/+ in front of any sub-expression, but the migrator only emits a unary sign when the operand is a primitive (a literal number/string or a plain identifier). A sign applied to a bracketed […] SGS reference, a parenthesised group, or a compound expression throws this error.

The message carries no line number — the failure is caught at file level, so only the file name is shown.

How generated scripts integrate with AMT & the Control Center

Integration happens at runtime, when the .ps1 runs inside a configured AMT environment. The library's Initialize / Connect-Application does three things:

  1. Loads the AMT COM engine — Add-Type -Path $global:ComScriptDll, then New-Object Asysco.Amt.Scripting.Comscript.
  2. Connects to the application — sets SysIniFile, AppName, Station="BATCH", ApplicationKind from Sys.ini / AmtSettings.xml, then Com.Connect().
  3. Creates the service objects — AmtMessage (Control Center), AmtFile (file controller), AmtScript/AmtReport (jobs), AmtPrint, AmtDatabase.
Caveat — these cmdlets are not standalone. They need AmtPsEclLib.psm1 imported, a valid Sys.ini/AmtSettings.xml, the ComScript DLL, and a live AMT app + Control Center. Run the .ps1 in plain PowerShell and the calls fail.

Start the local AMT175 Control Center

The AMT175 Control Center is hosted in IIS and authenticates against a local Keycloak. To bring it up on this PC you need three things running: Keycloak (port 8080), IIS with the AMT175 app pools, then browse to the CC URL.

URL: http://localhost/AMT175/ControlCenter  ·  Keycloak: http://localhost:8080 (realm amt175)

Step 1 — Start Keycloak (25.0.6) on port 8080

Open a PowerShell window and leave it running (Keycloak stays in the foreground):

⚠ ONE server only. Keycloak runs a single instance on 8080 — never start a second on 8081.
$env:KC_BOOTSTRAP_ADMIN_USERNAME='admin'
$env:KC_BOOTSTRAP_ADMIN_PASSWORD='admin'
cd 'C:\Tools\keycloak-25.0.6-fresh\keycloak-25.0.6'
.\bin\kc.bat start-dev --http-port=8080 --hostname=localhost --hostname-strict=false --db=dev-file

Ready when you see: Listening on: http://0.0.0.0:8080. Keep this window open; open a new PowerShell window for the next steps.

Be patient — this can take a while. A cold start (first run of the day, or after a reboot) can take 25–30 seconds or longer before it finishes booting, with the window looking idle in between. Do not close it — wait for the started in …s. Listening on: http://0.0.0.0:8080 line, which is your confirmation that Keycloak is up.

Successful startup looks like this (the key line is the last io.quarkus “started … Listening on” line):

Step 2 — Make sure IIS + the AMT175 app pools are running

⚠ Window 1 is busy running Keycloak — open a second, elevated PowerShell window (Run as administrator) for Steps 2 and 3. IIS usually auto-starts with Windows, so you only need Step 2 after a stop/restart.

The CC UI and its business-logic API run under IIS as /AMT175/ControlCenter and /AMT175/ControlCenterBL, in dedicated app pools:

Import-Module WebAdministration
Start-Service W3SVC                                   # IIS web service
Start-WebAppPool -Name 'AMT175_ControlCenterPool'     # CC UI
Start-WebAppPool -Name 'AMT175_ControlCenterBLPool'   # CC business-logic API

Step 2b — Start the AMT175 Windows services (elevated PS)

After the IIS pools are up, start the AMT175 runtime services. Run the following in the same elevated PowerShell window:

'AMT175_ApplicationManager','AMT175_ApplicationServer','AMT175_FileController','AMT175_BatchController' | ForEach-Object { Start-Service $_ }
⚠ CC Server Control icons stay yellow even when KC and IIS are running — this is because the AMT Windows services are stopped. Start the four services above first; the icons turn green only after they connect. AMT175_PrintController and AMT175_Reorganise may time out (error 1053) and can be left stopped — they are not required to run COBOL programs in CC.

Verify all four are running:

Get-Service AMT175_ApplicationManager,AMT175_ApplicationServer,AMT175_FileController,AMT175_BatchController | Select-Object Name,Status

# CC responds? (expect 302 -> .../realms/amt175/...auth = redirect to login)
curl.exe -s -i 'http://localhost/AMT175/ControlCenter' | Select-String '^HTTP/|^location:'

Stopping / restarting

Close the Keycloak window (Ctrl+C) to stop auth. To recycle the CC after a config change, touch its web.config (no restart needed):

(Get-Item 'C:\Amt\Parallel\AMT175\AmtTools\ControlCenterCore\web.config').LastWriteTime = Get-Date

Run a generated COBOL program in CC (Trial 3)

Runs the generated C# COBOL program via the AMT PowerShell runtime harness. The harness connects directly to the Application Server (port 4444) and submits a batch job — no CC Server Control required.

⚠ Prerequisites: Keycloak running, IIS app pools started, and all 4 AMT Windows services running (see Start the local AMT175 Control Center). Must use pwsh.exe (7.6.3) — NOT powershell.exe (5.1). The AMT assemblies target .NET 10 and will not load under PS 5.1.

Information — CobolToAmt Converter Settings
The converter stores its settings in the Windows Registry at HKEY_CURRENT_USER\Software\Asysco\CobolToAmt. The MostRecentSettings value holds the path to the last-used project settings file and is loaded automatically on startup — regardless of which version of the exe you launch. This means opening a freshly downloaded AMT177 build will pre-populate with the previous AMT172/175 working paths.

To start fresh: open regedit, navigate to HKCU\Software\Asysco\CobolToAmt and delete (or edit) the MostRecentSettings value — or simply use Load Settings / Save Settings in the UI to point to a new settings file, which will update the registry for future launches.
