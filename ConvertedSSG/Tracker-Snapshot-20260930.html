4 · Converter Fix — Data-Line Parse Bug (T3-001, Area B)

Root cause: COBOL data-division / output lines were emitted by running the whole line through the SSG expression migrator, so ordinary COBOL punctuation was misread as PowerShell operators — hyphens in names (PROGRAM-ID) as subtraction, PIC X(n) parentheses as unbalanced brackets, and level-number digits adjacent to a name (06 FILLER) as invalid tokens.

Before → after (CFH-COPY line 16)

# BEFORE (248 parse errors in the file)
DataLineOrNoStatement ((06 FILLER PIC  X( + ($FILLCTR + ").")))

# AFTER (0 parse errors)
DataLineOrNoStatement ("                     06 FILLER PIC  X(" + ($FILLCTR) + ").  ")

Fix: a new emit path builds each output line as a concatenation of verbatim double-quoted string segments (literal text) and only the [bracketed] references converted with variable context — so [FILLCTR]→$FILLCTR and [INPUT,1,1,1]→GetSgsValue("INPUT,1,1,1") resolve exactly as before. No change to bracket semantics.

Changed: SymstreamProcessor.cs (new OutputLineToPowerShellExpression + quoting helper; both DataLineOrNoStatement emit sites re-routed) and SymstreamExpressionMigrator.cs (made SplitBracketedReferencesAndLiteralParts public). Full write-up: SsgConverter-Fix-20260909.md.
Deployed 2026-09-10: library rebuilt; Build\Console and Build\Gui SsgConverter.dll refreshed (51200 bytes); Examples\Output goldens regenerated. All 5 parse 0; ARCHISEPARE (143) + CFH-COPY (47) run OK.

5 · Repeatable Routine

The whole fix→reconvert→verify loop is one script, so each new program follows the same steps: SsgConverter/Trials/Reconvert-And-Verify.ps1.

# rebuild library + refresh Build\Console&Gui DLL + regenerate goldens + verify
.\Reconvert-And-Verify.ps1 -Rebuild -RefreshDll -UpdateGoldens

# run one program through the Tier-1 harness
.\Trials\Tier1Mock\Run-SsgPsTrial.ps1 -Program CFH-COPY -Diff
Run overwrites with VS Code closed. While VS Code is open, its extensions hold OS read-locks on the loaded .dll (C# service) and analysed .ps1 (PowerShell/PSScriptAnalyzer). External processes cannot overwrite the Build\Console DLL or the Examples\Output goldens until VS Code is closed. In-editor edits are unaffected. Backups: SsgConverter/_backup/Output-* and SsgConverter.dll.orig.
"Access denied" can also be plain UAC, not the VS Code lock above (found 2026-09-30, T3-009). ACLs under SsgConverter\Source\ and SsgConverter\Build\ grant write only to BUILTIN\Administrators/ SYSTEM; an unelevated session shows the account's Administrators membership as "Group used for deny only" (whoami /groups) and gets only Users-level (read/execute) rights — so both a VS Code save ("Insufficient permissions... Retry as Admin") and -RefreshDll's Copy-Item fail with "Access to the path ... is denied", closed VS Code or not. Fix: re-run the write step (save, or Reconvert-And-Verify.ps1 -RefreshDll) from an elevated pwsh/VS Code — the account already has the rights, it just isn't using them. Distinguish the two causes with Get-Acl + whoami /groups before assuming a lock.

Stage A runbook — run against the real AmtPsEclLib (Area D)

Proves the converted .ps1 is API-compatible with the real AMT runtime — using an isolated copy of the runtime libraries, with no COM object and no app connection. One command:

cd SsgConverter/Trials/RealRuntime
pwsh -NoProfile -File .\Run-StageA.ps1 -Program CFH-COPY

What the runner does, in order:

  1. Import the isolated runtime. Trials/RealRuntime/AmtPsEclLib.psm1 (+ AmtPsSortLib.psm1) — read-only copies; never the Federale_InternalRelease original.
  2. Isolated init. Set $global:WarningRcw2435 = $false — the one Initialize-scope flag Fin reads (AmtPsEclLib L6051) that is not set at module load. The statement-context globals (PreviousStatement, InSsg, …) are already set at import.
  3. Seed SGS. $global:SgsLabels = New-Object Dictionary[String,Object] then AddTo-SgsList for INPUT ECL-TAPEIN,80,1 / OUTPUT ECL-TAPEOUT,80,1 / ASCII 1.
  4. Run Examples/Output/CFH-COPY.ps1 -Parameters @('80').
Result (2026-09-10): the full program body executes against the real runtime and prints FIN → End Job → Script Done — exit 0. The only remaining step is the end-of-job COM cleanup $global:Com.RemoveNonPrintedFiles() (AmtPsEclLib L3157), an unguarded COM call that needs the COM object created only by the Stage B bring-up. Run-StageA.ps1 recognises this exact boundary and reports PASS (Stage A).
Why Stage A stops here. Initialize (AmtPsEclLib L497) is not isolated: it Add-Types ComScript.dll, creates the COM object, and calls Connect-Application against the live app. Running it — and letting the COM cleanup complete for real — is Stage B (MT-005). Do not mock $global:Com: a stub only triggers further COM property accesses (e.g. .Station in the logging path) — re-mocking the whole object is Stage B.

5c · AMT Control Center Run Process (Stage B) — developer walkthrough

How a converted report is run as a real AMT job under Control Center / BatchController on this VM — written so a developer can follow it by hand. Two tiers share the same run process; only the artefact + catalog type differ:

TierArtefactRunnerStatus
Tier 2 (SSG→C#)compiled <Program>.dll in Binaries\Reports\BatchController runs the DLL itself via LoadAndRunReportproven (AMT175)
Tier 3 (SSG→PS)converted <Program>.ps1 using AmtPsEclLibBatchController hands off to AmtPowershellHost.exe (net8 / PS 7.4) which carries the DB/SqlClient deps closureour target
Why not standalone pwsh. A converted .ps1 run in a bare pwsh reaches Connect-Application but fails the DB connect: the native MsSql wrapper (Asysco.Amt.AmtSqlServerWrapper.dll, selected by SERVER TYPE=MSSQL in Sys.ini) needs a .NET 8 closure (Microsoft.Data.SqlClient 6.1.4 + native SNI 6.0.2) that only exists via a .deps.json. Bare pwsh has none → “not supported on this platform.” Run it under the shipped host instead (below). See MT-005.

  1. Confirm the stack is up. Get-Service Federale* | ? Status -ne 'Running' returns nothing. (Full cold-start order: Keycloak → IIS/CC site → FileController → BatchController → TransactionServer.)
  2. Deploy the artefact. Tier 2: copy <Program>.dll to AFBUS_AMT\Binaries\Reports\. Tier 3 (PS): the report must be wrapped in the CC job skeleton (SsgConverter emits body-only — MT-008) and placed 2 levels deep at Scripts\<GROUP>\RUN\<name>.ps1 so its Import-Module ..\..\Libraries\AmtPsEclLib.psm1 and $AmtSettingsFile="..\..\Settings\AmtSettings.xml" resolve. A real Scripts\Settings\AmtSettings.xml must exist (only .sample ships).
  3. Register in the catalog. Control Center → System Configuration → Batch & Forms → AvailableJobs → Read all jobs from system (a scan; there is no manual “Add”). The row is App / JobName / Description / Type / Queue / File; a PowerShell report is Type Script (vs AmtReport for a DLL). Confirm a Script-type row for your program appears (filter by Jobname).
  4. Make the BatchController see it. If needed, Restart-Service FederaleBatchController (elevated) so it rescans. No live auto-sync.
  5. Activate the job. Control Center → Security → Jobs → Activate (else it never appears under Start Job).
  6. Stage input files. Read the report’s DISC designators (for a PS report, the INPUT/OUTPUT SGS names it reads, e.g. ECL-TAPEIN / ECL-TAPEOUT). Copy fixtures to <working base>\Lion\Files\Extracts\<designator>.DAT immediately before Start Job (designators are shared across programs).
  7. Start the job. Control Center → Jobs → Start Job → app → job → Start. This inserts a row in AMTSYSBATCHREQUEST. Typical runtime params: LOADINBATCHCONTROLLER /R:19 /USEWORKINGDIR.
  8. Monitor. Control Center → Job Management / Batch Control: Queued → Running → Completed (backed by AMTSYSPROCESSJOB). Watch the joblog appear under AmtTools\Basepaths\Logs\<date>\ and Event Viewer.
  9. Collect output. Read output from the same Extracts folder by the output designator (e.g. ECL-TAPEOUT).

# CFH-COPY.ps1 wrapped for Control Center (Type: Script) - deploy to Scripts\<GROUP>\RUN\
Import-Module -Name "..\..\Libraries\AmtPsEclLib.psm1"  -Force -DisableNameChecking -ErrorAction Stop

Set-Jobname "CFH-COPY"
Initialize $AmtSettingsFile
Try {
  # SGS seed (from the Trial3 manifest / Tier-1 sgs-values.json)
  AddTo-SgsList "INPUT ECL-TAPEIN,80,1"
  AddTo-SgsList "OUTPUT ECL-TAPEOUT,80,1"
  AddTo-SgsList "ASCII 1"
  # ... converted report body (Examples\Output\CFH-COPY.ps1, minus its trailing Fin) ...
  Fin
} Catch [Exception] {
  HandleTrapAndAbort "Error trapped: " $_
} Finally {
  Cleanup $false
}

T3-006260917A Tier-1 mock's GetSgsValue returned raw strings, not typed values. PowerShell treats the string "0" as truthy (only "" is falsy) but the int 0 as falsy. CFH-COPY's converted script guards its MAXCOPY block with a raw If ((GetSgsValue ("MAXCOPY"))) (no CompareTypeSafe) — with MAXCOPY=0 (disabled) the string mock wrongly entered the block, emitting 2 extra lines (a COPY-LIMIT declaration + a GO TO FINW check that would break the copy loop at runtime). The same untyped-string return also broke raw *SET arithmetic (string concatenation instead of addition, e.g. ARCHIFORMAT's $A computed as 10554 instead of the documented 69). Fixed by coercing numeric-looking mock values to [Int64]/[Double] in GetSgsValue (SsgPsMockLib.psm1), matching the real typed SGS store. Confirmed via an A/B test shadowing the old vs new behaviour side by side. CFH-COPY's emitted line count corrected 47→45 in §3. ✓ fixed · 260917
T3-007260924A PowerShell Hashtable member-shadowing silently broke SGS seed loading. Reset-SgsMock/GetSgsValue used .Keys/.ContainsKey() (dot-notation) on the seeded Hashtable. When a seed file contains a key that matches (case-insensitively) a real Hashtable member name — e.g. LECTIS_ASCII's SSG condition flag literally named KEYS — PowerShell's ETS silently resolves .Keys to that dictionary entry's value instead of the real key collection, collapsing enumeration to one phantom item (0) and defaulting every other seeded key to 0 with a false "no mock value" warning (63 of 80 lookups on LECTIS_ASCII's first run, even for keys that were seeded, e.g. ASCII). Fixed by using .PSBase.Keys / .PSBase.ContainsKey() / .PSBase.Count throughout SsgPsMockLib.psm1 and Run-SsgPsTrial.ps1, which bypass the ETS adapter. Any future program with an SSG condition/param literally named Keys, Count, Values, Add, etc. would hit the same hazard without this fix. ✓ fixed · 260924
T3-008260924A Missing Log-Message primitive in the mock harness. RECAP's converted script calls Log-Message $Text $Severity (the real AMT logging primitive, e.g. Log-Message ("schema = " + $schname) '([LogMessageType]::Information)'); the Tier-1 mock lacked it → runtime throw (The term 'Log-Message' is not recognized...). Added Log-Message to SsgPsMockLib.psm1 (records the call for visibility, otherwise a no-op — same pattern as T3-002 Hdg / T3-004 SetC) — unblocked RECAP. ✓ fixed · 260924
T3-009260929B Leading-+ *INCREMENT variable name produced an invalid/mismatched For loop. CONDIS2_ASCII writes *Increment +I FROM 1 BY 1 TO [PG] — some SSG sources put the leading + on the loop variable name itself (not as an operator); every other reference to the same loop variable in the source (e.g. bracketed [PG,I,1,1]) omits the +. The converter captured the raw +I as the declare (For ([Int32]$+I = 1; ...) — invalid PowerShell) while a separate vendored AST-writer path sanitised condition/increment references (leading +→_) to $_I, producing a declare/condition mismatch even once the syntax was patched around. Fixed by stripping a leading + from incrementVariable right after regex capture in SymstreamProcessor.cs (DirectiveId.Increment). The analogous *DO variable capture has the same latent pattern but was left unfixed — no confirmed repro there. Rebuilt/redeployed 260930 with no regressions across the other 17 programs; unblocked CONDIS2_ASCII (18th program, 0 parse errors, runs clean). Independently reconfirmed 260930: EXTEUR (19th program) uses the identical *Increment +I/+J construct (nested, nested two levels deep) and also parsed 0 / ran clean with no further fix needed — a second, unrelated source file exercising the same code path. ✓ fixed · deployed 260930

8 · How to Update This Page

This page is maintained / updated via VS Code Copilot, driven by the repository’s Copilot instructions — not hand-edited ad hoc. The always-on contract is .github/copilot-instructions.md; deeper, on-demand rules live in the area instruction files: .github/instructions/ssg-run-trials.instructions.md (Area A), ssg-converter-dev.instructions.md (Area B), ssg-reconvert.instructions.md (Area C), ssg-amtcc-runbook.instructions.md (Area D), and ssg-todo-issues.instructions.md (the T3-nnn / MT-nnn registers). Repeatable work is driven by the /ssg-* prompts in .github/prompts/ (/ssg-run-trial, /ssg-fix-converter, /ssg-reconvert, /ssg-e2e, /ssg-update-tracker, /ssg-session-start, /ssg-review) and the reusable scripts Reconvert-And-Verify.ps1, Trials/Tier1Mock/Run-SsgPsTrial.ps1, Trials/RealRuntime/{Run-StageA.ps1, Run-StageB.ps1, Deploy-CC-Job.ps1}. Larger changes are captured as plan files in .github/Copilot_Plans/ and referenced/linked from the related MT-nnn ToDo entries (and T3-nnn issues). Whenever any of these change, the driving Copilot session — following the instruction files above — updates the affected registers (§3/§6/§7), the plan files, and this page in the same pass so they don’t drift. The explicit mechanism is the /ssg-update-tracker prompt, invoked as the closing action of a reviewed run (see the area instruction files); it is a Copilot convention enforced by those instructions, not an automated build step, so it depends on the agent honouring them each session.

After bringing a program online (parse 0 + harness run), add or update its row in §3: set the before→after parse counts, the run badge (✓ runs once it executes), emitted line count, and notes (link any relevant T3-nnn issue). Refresh the Last updated date and the §1 current-state box.

When a new bug is found, append a T3-nnn row (§6); when a new pipeline function / feature is needed, append an MT-nnn row (§7) with a yymmdd created date. Conventions: .github/instructions/ssg-todo-issues.instructions.md.
