## 1. "Converted" is not "supported": the example of RECAP's `ASCIIFD` branch

"Converted" happens at two levels, and `ASCIIFD` sits differently in each:

| Level | Is `ASCIIFD` in it? | Does it ever run? |
|---|---|---|
| **The converted skeleton** (`UTILIT_RECAP.ps1`, made mechanically by SsgConverter) | **Yes.** The converter converts the whole skeleton, every branch whether used or not. The `ASCIIFD` logic is there: 12 tests such as `If (GetSgsValue "ASCIIFD") = 1 …`. | **No.** On the generic route the deployed skeleton calls the hand-off and then returns, so its body never runs. |
| **The generic program** (`RECAP_GN`, hand-made) | **No.** It has no `ASCIIFD` or `DISP-1` code at all. | **No code to run.** |
| **The hand-off** (`RecapParm.ps1`) | It **refuses** the card: `L1 ASCIIFD (Fieldata records) not supported`. | Only if a call ever gives `ASCIIFD`. Then the job stops before the program, with that message. |

So the `ASCIIFD` path is converted, but not supported or executed:
- **Converted**, as part of the mechanical skeleton conversion.
- **Not supported:** the generic program, which is what actually runs on AMT, leaves the branch out, because no real call
  uses it. It also couldn't be tested: Fieldata `DISP-1` records don't exist on AMT.
- **Not executed:** the skeleton's own copy never runs, and a call that asks for it is refused rather than given a guessed result.

"No real caller" means: none of the real calls (every `@SSG … *UTILIT.<skeleton>` in the 1,080 indexed production
runstreams; 170 contain one, 371 calls) gives the card that switches that branch on. The branch exists in the source
and in the converted skeleton, but it is not used to specify the generic program, because no real call's cards in
production use it.

## 2. If Federale later runs a job that needs a refused branch

**1. The job is refused, visibly.** The hand-off sees the card before the program runs and stops the job with `Abort`,
e.g. `SSG-4 hand-off (RECAP): L1 ASCIIFD (Fieldata records) not supported`. Nothing is written and no wrong output is
produced; the failure points straight at the card.

**2. Who can extend the program depends on when it happens.** We do the conversion for Federale; we do **not** leave Federale
with the conversion tools (skeleton expansion, reference models, parameter cross-checks, the G1–G8 pipeline). So:

| When the refused branch is found | Who can add it | How |
|---|---|---|
| **Before handover** (our pre-go-live scan, or Federale's testing) | us, as part of the conversion | the same G-steps, scoped to the new branch (table below); the existing baseline must stay unchanged |
| **After handover** | **not Federale with our tools.** Either a change request back to the conversion supplier, or Federale maintains the delivered objects as ordinary application code: the generic program is a normal COBOL object in LionDev (`<U>-GN`, C# generated by AMT) plus a PowerShell include (`<U>Parm.inc`) | a supplier change goes through the G-steps; Federale's own maintenance would be ordinary programming and testing **without** the model, cross-check and regression we use |

So the refusal is safe (visible, nothing wrong written), but it moves work to after go-live, where it is more expensive and
done without our proof tooling. That is the main argument for closing the gap **before** handover (§3, option B or C) and for
the pre-go-live scan (point 4).

The G-steps for an extension (before handover, or by the supplier on a change request):

| Step | For the new branch |
|---|---|
| G1 | add the new real call to the inventory |
| G2 | extend `spec.md` from the **SSG source** (layout, behaviour, assumptions) — gate |
| G3 | extend the reference model and add test cases for the branch |
| G4 | add the branch to `<U>-GN.cob` (0 conversion errors) |
| G5 | the writer passes the new card instead of refusing it, and its must-reject case is removed |
| G7 | the existing baseline must stay **unchanged**, plus the new call matches — gate |
| G8 | build, LionDev, deliver, then a CC run of the new cases **plus the full regression of that utility** — gate before release |

The work is limited to that branch. All the existing calls must still give byte-identical results.

**3. Some branches can't be supported just by extending the program.** Those cases need a decision by the business
analysts, not only conversion work:
- **No AMT equivalent:** Fieldata records (`ASCIIFD`, TABAN without `ASCII`), tape, card reader. The data or the run itself
  would have to change, e.g. to ASCII files.
- **A routine missing from the target:** e.g. TABAN's `Y2K` branch needs `CDTOAF`. The routine must be supplied first, like
  `EUU003` today.
- **OS 2200 behaviour unknown:** the expansion then needs an answer from Eddy (as Q7/Q11 did), or a pushed-through assumption.

**4. It can be caught before go-live, not in production — and should be, because after handover Federale cannot extend the
program with our tools.** The refused cards are a known list per utility (tracker §3b). Scanning the final production
runstream set for those cards, with the same card export we already use, would show any such call in advance.

## 3. The completeness gap: source logic with no counterpart in the target

**The rule behind "the spec comes from the source".** It is an evidence rule about the *definition* of the behaviour, not a
ban on reusing code:
- `ssg-generic-utility.instructions.md` line 60: *"The reference model is built from `spec.md` and the SSG source only,
  never from converter output."*
- `ssg-generic-utility.prompt.md` (G2), line 79: *"Source only: the SSG skeleton (read-only) and the expansions. Never
  converter PowerShell as the definition."*

The reason is independence: if the spec or model came from converter output, a converter bug would be copied into the
expected result and could never be caught (T3-070's `NEURO` is an example). Separately, the skeleton's converted `ASCIIFD`
code couldn't be reused anyway: it writes COBOL text for one call, not logic the generic program can run.

**The concern (owner 261118).** There are elements of the SSG/COBOL logic that are not built in. They would be untested
anyway, as no path exists, but there is also no untested logic sitting in a matching target routine, so for those parts we
cannot say "source program and target routine: proven" or "unproven". Today the claim is "the target equals the source
**for the supported subset**"; for refused branches the source logic has no counterpart. There is no complete statement,
branch by branch, of what the source contains and how far the target matches it.

**Ways to close it:**

| Option | What the target then holds for an unused branch | What can be claimed | Limits |
|---|---|---|---|
| **A. Coverage matrix** (documentation) | Nothing new. A table per utility of every card-driven branch of the skeleton (`*IF [LABEL…]`, with the skeleton line), each marked *implemented + proven by real calls*, *implemented + proven by test data*, or *not implemented: refused, with its must-reject test*. Mostly generated by scanning the skeleton and the real calls' cards. | A complete, auditable source↔target map: every source branch is accounted for, and "not converted" is itself a tested statement. | Refused logic still isn't in the target. |
| **B. Implement every implementable branch**, proven with labelled test data (as LECTIS does today) | The logic, built from the SSG source and proven against the model on test data. | "Implemented and proven against the source's behaviour, not against a real call." | More work per utility. Branches with no AMT equivalent (Fieldata, tape, card reader) or a missing routine (`CDTOAF`) still can't be built, so A is still needed for those. |
| **C. B for the likely-used branches, A for the rest** | A mix. | As B and A. | Needs a business view of which branches matter. |

Suggestion: A in any case (it gives the proved/unproved view per source branch), and B or C on top where Federale's
analysts think a branch may be used in future.

## For Conversion Scope / Federale to decide

1. Is "equal for the supported subset, every other branch refused and listed" acceptable for go-live, or must every
   implementable source branch exist in the target (option B/C)? Note that after handover Federale does not have the
   conversion tools, so any branch added later is a change request or ordinary maintenance without our proof tooling.
2. Which refused branches might Federale use in future (input for option C)?
3. Who runs the pre-go-live scan of the final production runstream set for refused cards, and against which drop?
4. For branches with no AMT equivalent (Fieldata, tape, card reader): change the run or the data, or accept the refusal?
5. After handover, if a refused branch is needed: change request to the conversion supplier, or Federale's own maintenance
   of the delivered program (LionDev object + PowerShell include)? Is that in the support agreement?
