# Install AMT MCP Servers

The AMT MCP servers run as **.NET tools** pulled straight from the **AMT_Mcp**
Azure Artifacts feed via `dotnet dnx`. There is **nothing to build locally** and
**no absolute paths to edit** — VS Code launches each server on demand and the
feed download is cached per machine. Every migration project reuses the same
published tools.

> **Azure DevOps golden rule:** all Azure DevOps work (work items, repos, PRs,
> pipelines, wiki, test plans) MUST go through the `<project>-ado` MCP server.
> **Never use the `az` CLI (`az boards` / `az repos` / `az pipelines`) or raw
> REST for Azure DevOps** — the MCP is the sanctioned interface, works without a
> CLI install, and uses the signed-in Microsoft account. If the ADO MCP tools
> are missing, fix the server (see the `<project>-ado` section below) rather than
> falling back to `az`.

## What you get

All servers are defined **once** in the project repo's `.vscode/mcp.json`
(e.g. `<Project>_Migration/.vscode/mcp.json`), each name **project-prefixed**
(`<project>-…`) so it never collides with another workspace folder, the
user-level `mcp.json`, or another project. Package IDs are **unpinned**, so each
server runs the **latest** version on the feed.

| Server (`<project>-…`) | Feed package (`dnx`) | Source project | Purpose |
|---|---|---|---|
| `<project>-ado` | npm `@azure-devops/mcp` (via `npx`, no feed) | — | Azure DevOps work items / repos / PRs |
| `<project>-iis` | `Asysco.Amt.Mcp.Iis` | `IISMCP` | Inspect/manage IIS sites & app pools |
| `<project>-event-viewer` | `Asysco.Amt.Mcp.EventViewer` | `EventViewerMCP` | Windows Event Log queries |
| `<project>-net-debug` | `Asysco.Amt.Mcp.NetDebug` | `NetDebugMCP` | Attach/inspect .NET processes (Windows-only) |
| `<project>-lion-repository` | `Asysco.Amt.Mcp.LionRepository` | `LionRepositoryMCP` | that project's Lion repository DB |
| `<project>-amt-config` | `Asysco.Amt.Mcp.AmtConfig` | `AmtConfigurationManagerMCP` | that project's ControlCenter BL + Keycloak |
| `<project>-amt-script` | `Asysco.Amt.Mcp.AmtScript` | `AmtScriptMCP` | that project's AMT runtime (sys.ini) |
| `<project>-keycloak` | `Asysco.Amt.Mcp.Keycloak` | `KeyCloakMCP` | that project's Keycloak realms/clients/users |

**Feed:** `https://pkgs.dev.azure.com/avanade-lt-coe/AMT_Products/_packaging/AMT_Mcp/nuget/v3/index.json`
(org `avanade-lt-coe`, project `AMT_Products`, feed `AMT_Mcp`).

The **project-bound** servers (`lion-repository`, `amt-config`, `amt-script`,
`keycloak`) are the same shared tool pointed at a *specific project's*
database/runtime via `--settings <path>` (see below). The rest are
project-agnostic.

## Prerequisites

1. **.NET SDK 10** on `PATH` (`dotnet --version`) — provides `dotnet dnx`.
2. **Node.js 20+** on `PATH` (`node -v`) — only for `<project>-ado`, launched
   via `npx`. npm must resolve packages from the **public** registry
   (`https://registry.npmjs.org/`); a mis-set private registry causes an npm
   `E401` before the server even starts (see the `<project>-ado` section).
3. **Access to the `AMT_Mcp` feed** in Azure DevOps (org `avanade-lt-coe`,
   project `AMT_Products`).
4. **Azure Artifacts Credential Provider** installed so `dnx` can restore from
   the feed silently (MSAL). It is **not** bundled with the .NET SDK and does
   **not** use your Windows login. Without it the first restore fails with a 401.
   Install it once per machine:
   ```powershell
   iex "& { $(irm https://aka.ms/install-artifacts-credprovider.ps1) }"
   ```
   With an existing Azure DevOps / Entra sign-in, auth is then **silent** — no
   browser, no PAT — and the token is cached and reused. The first restore may
   pop an interactive sign-in; after that the token is cached.

   The provider is just a NuGet plugin (nothing runs in the background). Where it
   lives and how to inspect it:
   ```powershell
   # Plugin DLLs (dotnet/dnx uses the netcore one):
   #   %USERPROFILE%\.nuget\plugins\netcore\CredentialProvider.Microsoft\
   #   %USERPROFILE%\.nuget\plugins\netfx\CredentialProvider.Microsoft\   (classic nuget.exe)
   Get-ChildItem "$env:USERPROFILE\.nuget\plugins" -Recurse -Filter CredentialProvider.Microsoft.dll |
     ForEach-Object { $_.FullName; (Get-Item $_.FullName).VersionInfo.ProductVersion }

   # Cached token (why non-interactive VS Code launches work):
   #   %LOCALAPPDATA%\MicrosoftCredentialProvider\SessionTokenCache.dat
   Get-ChildItem "$env:LOCALAPPDATA\MicrosoftCredentialProvider"
   ```

> No sibling-clone layout or specific workspace-folder name is required anymore —
> the servers come from the feed, not from a built `amt-go-net` checkout.

## Steps

### 1. Ensure feed auth works

From any folder, prime the credential provider once (any server package works).
Use `--interactive` the **first** time so it can pop a sign-in if there is no
cached token yet (VS Code launches servers non-interactively, so the token must
already be cached before first server start):

```powershell
dotnet dnx Asysco.Amt.Mcp.Iis --source "https://pkgs.dev.azure.com/avanade-lt-coe/AMT_Products/_packaging/AMT_Mcp/nuget/v3/index.json" --interactive --yes --help
```

If this downloads and runs without a 401, auth is set up (once signed in, drop
`--interactive` — it restores silently from the cached token). To **force a fresh
sign-in** (expired token / wrong account), delete the cache first:

```powershell
Remove-Item "$env:LOCALAPPDATA\MicrosoftCredentialProvider\SessionTokenCache.dat" -ErrorAction SilentlyContinue
```

then re-run the command above with `--interactive`.

### 2. Fill in the project-bound settings

Under `<Project>_Migration/amt-mcp/`, copy each `<name>.appsettings.json.sample`
to `<name>.appsettings.json` (gitignored) and fill in your environment — URLs,
DB, and any secret (see "Project-bound server config" below).

### 3. Open the project workspace

Open the project's `.code-workspace` (e.g. `<Project>_Migration/<Project>.code-workspace`),
or the `<Project>_Migration` folder directly — the committed `.vscode/mcp.json`
is self-sufficient either way.

### 4. Trust and verify

On first start VS Code prompts to trust each server and `dnx` downloads each
package (first launch is slower). Then run **MCP: List Servers** from the Command
Palette and confirm all eight are `Running`. If one is missing, **Show Output**
on it to see why (usually a feed-auth 401 or a bad settings path).

## Azure DevOps server (`<project>-ado`)

This is the odd one out: it is **not** a `dnx` feed tool. It runs the public npm
package `@azure-devops/mcp` via `npx`, so it depends on two machine-local things
that the committed `mcp.json` cannot supply — **Node/npm** and a **Microsoft
sign-in**. "Same config" is not enough; each machine must satisfy both.

### Auth: Microsoft account, not `az`

The server authenticates with the **signed-in Microsoft account** (interactive
sign-in on first use, then a silent MSAL token cached under
`%LOCALAPPDATA%\.IdentityService`). It does **not** require the Azure CLI and does
**not** read a PAT from the config. So:

- It works when you are signed in with an `@avanade.com` account that has access
  to the `avanade-lt-coe` org — complete the sign-in prompt the first time the
  server starts.
- Wrong account/tenant, or an account without org/project access, → the tools
  fail even though `az` might work. Fix the sign-in, do not switch to `az`.
- (The package also supports `--authentication azcli`, but we deliberately do
  **not** use it — keep auth on the Microsoft-account path.)

### npm must use the PUBLIC registry

`npx` has to download `@azure-devops/mcp` from `https://registry.npmjs.org/`.
If npm is pointed at a private/authenticated registry (a corporate mirror or an
Azure Artifacts npm feed) whose token is missing or expired, the download is
rejected and the server dies at startup with:

```
npm error code E401
npm error Incorrect or missing password.
```

This is an **npm package-download failure**, not an Azure DevOps auth problem —
the MCP never initializes (`process exited with code 1`).

**Diagnose:**
```powershell
npm config get registry     # want: https://registry.npmjs.org/
npm config ls -l            # shows which .npmrc files are in play
```
Also inspect the `.npmrc` files it lists (user `%USERPROFILE%\.npmrc`, plus any
global `%APPDATA%\npm\etc\npmrc` / `%ProgramData%` one) for a `registry=` line
pointing at a private feed and any stale `_auth` / `_authToken` / `_password`.

**Fix — pick one:**
- If the private feed must stay the default (corporate policy — e.g. an Azure
  Artifacts npm **mirror** like `AMT_Mirror` set as `registry=` in the user
  `~/.npmrc`), the token is just **expired** — refresh it with `vsts-npm-auth`
  (this is the common case; the mirror upstreams the public registry so once the
  token is fresh `@azure-devops/mcp` resolves again):
  ```powershell
  # vsts-npm-auth needs a project .npmrc that names the feed registry:
  Set-Content .npmrc "registry=<feed-url>`nalways-auth=true"
  # Run the .cmd wrapper, NOT vsts-npm-auth directly: the .ps1 shim is unsigned
  # and blocked by execution policy ("file is not digitally signed").
  & "$env:APPDATA\npm\vsts-npm-auth.cmd" -config .npmrc -force
  npm view @azure-devops/mcp version   # confirms auth (prints a version)
  ```
  Then delete the temporary project `.npmrc` (the refreshed token lands in the
  user `~/.npmrc`) and reload the `<project>-ado` server. This is a **session
  token that expires** — re-run the same refresh whenever E401 recurs. If
  `vsts-npm-auth` isn't installed: `npm i -g vsts-npm-auth`. `npm login
  --registry <feed-url>` is the manual alternative. The npm debug log path
  printed in the error names the exact registry URL that returned 401.
- Point npm back to the public registry (simplest, ONLY if the private default
  isn't required by policy):
  ```powershell
  npm config set registry https://registry.npmjs.org/
  ```
  then reload the `<project>-ado` server.
- Config-level guard (only if the public registry is reachable and not blocked by
  policy): force this one fetch to the public registry in `mcp.json` —
  `"args": ["-y", "--registry", "https://registry.npmjs.org", "@azure-devops/mcp", "<org>"]`.
  Do **not** do this where teammates are required to route npm through a mirror.

### Version note

The package is unpinned (`-y` pulls latest). v2.9+ renamed/consolidated the tool
names; if that breaks agents, temporarily pin `@azure-devops/mcp@2.8.1` in the
`args`.

## Getting the newest build

Package IDs in `mcp.json` are **unpinned**, so `dnx` resolves the latest version
published to `AMT_Mcp` each time it restores. To pick up a freshly published
server:

- **Reload the MCP server** (MCP: List Servers → restart it), or reload the
  window. `dnx` re-resolves and, if a newer version exists, downloads it.

New versions reach the feed via the `pipelines/amt-mcp.yml` pipeline, which packs
all seven tool projects and pushes them (triggered on `develop` changes under
`Tools.Net/MCP/**`). Building locally is **not** part of the install flow.

## Project-bound server config (per project)

Each project-bound server reads a settings file from the project repo, passed via
`--settings`. Under `<Project>_Migration/amt-mcp/` you have, per server:

- `<name>.appsettings.json.sample` — **committed** template with placeholders
  (`CHANGE_ME`) and inline notes. This is the *only* config file checked in.
- `<name>.appsettings.json` — **gitignored**, USER-SPECIFIC. Copy it from the
  `.sample`, then fill in your environment (URLs, DB, and any secret) here.

There is **no sharable config** and **no base/local overlay** — every value
(server URLs, DB names, paths, credentials) can differ per machine, so the whole
`.json` is user-specific and never committed. `mcp.json` points `--settings` at
`<name>.appsettings.json`. Everything under `amt-mcp/` is ignored via
`/amt-mcp/*.json`; the `.json.sample` templates are what teammates commit.

First-time per project: copy each `<name>.appsettings.json.sample` to
`<name>.appsettings.json` and set the real values (including secrets).

### Fill order & where each value comes from

The project-bound servers form a dependency chain, so configure them in this
order — most values can be **discovered with the previous server's tools**, and
only a few are truly hand-supplied:

1. **`iis`** (no config) and **`keycloak`** first. Keycloak is the root of trust:
   `BaseUrl`, `AdminUsername`, `AdminPassword`, `DefaultRealm` (=`master`) are all
   **hand-supplied** (Keycloak master admin creds — nothing to discover). Auth is a
   password grant via the `admin-cli` client against the `master` realm.
2. **`amt-config`** — derive from keycloak (+ `iis`):
   - `KeycloakTokenUrl` = `{Keycloak BaseUrl}/realms/{realm}/protocol/openid-connect/token`;
     get the AMT realm (e.g. `AmtWorking`, **not** `master`) from keycloak `list_realms`.
   - `ClientId` — keycloak `list_clients <realm>` → the confidential (public=false)
     client, e.g. `amt-config-mcp`. **On a fresh system this client may not exist yet** —
     create it with keycloak `create_client` (confidential, `serviceAccountsEnabled`) and
     grant it the ControlCenterBL audience/roles.
   - `ClientSecret` — keycloak `get_client_secret <clientId> <realm>` (or
     `regenerate_client_secret`).
   - `ControlCenterBlUrl` — `iis` `list_sites` (binding → scheme/host/port) +
     `list_applications` → the `/…/ControlCenterBL` app path.
3. **`amt-script`** — with amt-config working: `AppName` + `ApplicationKind` come from
   amt-config `list_applications` (e.g. `MYAPP_AMT` / `CobolOS2200`). `SysIniFile` is a
   local path (standard `C:\Amt\Working\sys.ini`).
4. **`lion-repository`** — standalone; **hand-supply** the SQL host + DB for the Lion
   **developer repository** (e.g. `WORKING_REPOS`). Note this is *not* one of
   amt-config's database settings (those are runtime app DBs).

> **Every machine differs — re-derive, don't copy.** Realm name, `ClientId` (may be
> absent → create it), ControlCenterBL host/port/path, and the SQL host can all change.
> Always hand-supplied: Keycloak admin credentials, the `sys.ini` path, and the
> repository DB login.

### What each server's settings contain

Point every server at *your* environment by editing your gitignored
`<name>.appsettings.json` (copied from the `.sample`).

**`lion-repository.appsettings.json`** → the Lion repository DB:
```jsonc
{
  "Repository": {
    "DatabaseServer": "localhost",     // SQL Server host\instance
    "DatabaseName": "WORKING_REPOS",   // Lion repository DB
    "IntegratedSecurity": false,       // true = Windows auth (UserName/Password ignored)
    "UseSsl": false,
    "ReadOnly": false,                 // true to block all write tools
    "StoreRevDataBlob": false,
    "UserName": "asy",                 // only used when IntegratedSecurity is false
    "Password": "CHANGE_ME"
  }
}
```

**`amt-config.appsettings.json`** → ControlCenter BL + Keycloak (for tokens):
```jsonc
{
  "AmtConfig": {
    "ControlCenterBlUrl": "http://localhost/Working/ControlCenterBL",
    "KeycloakTokenUrl": "http://localhost:8080/realms/AmtWorking/protocol/openid-connect/token",
    "ClientId": "amt-config-mcp",
    "ClientSecret": "CHANGE_ME"
  }
}
```

**`amt-script.appsettings.json`** → the AMT runtime (no secret):
```jsonc
{
  "ComScript": {
    "SysIniFile": "C:\\Amt\\Working\\sys.ini",  // AMT runtime sys.ini
    "AppName": "MYAPP_AMT",
    "ApplicationKind": "CobolOS2200",
    "JobName": "AmtScriptMCP",
    "Station": "",
    "User": "",
    "ReadOnly": false
  }
}
```

**`keycloak.appsettings.json`** → Keycloak admin API:
```jsonc
{
  "Keycloak": {
    "BaseUrl": "http://localhost:8080",
    "AdminUsername": "admin",
    "AdminPassword": "CHANGE_ME",
    "DefaultRealm": "master"
  }
}
```

## Gotchas (known, load-bearing)

- **Azure DevOps = the `<project>-ado` MCP, never `az`.** Do all ADO work
  (boards/repos/PRs/pipelines/wiki/test-plans) through the MCP tools. If they are
  unavailable, repair the ado server (Node/npm registry + Microsoft sign-in) —
  do not fall back to the `az` CLI or raw REST.
- **`<project>-ado` npm `E401` at startup = wrong npm registry**, not an Azure
  DevOps auth failure. npm can't download `@azure-devops/mcp` from a private
  registry with a missing/expired token. When a corporate Azure Artifacts npm
  mirror (e.g. `AMT_Mirror`) is the default `registry=`, the usual cause is an
  **expired session token** — refresh it with `vsts-npm-auth.cmd -config .npmrc
  -force` (use the `.cmd`; the `.ps1` shim is execution-policy-blocked). Otherwise
  point npm at the public registry (or fix the feed token) — see the
  `<project>-ado` section.
- **`<project>-ado` starts but tools 401/return nothing = Microsoft sign-in.**
  Complete the interactive sign-in with an `@avanade.com` account that has
  `avanade-lt-coe` access; check org/project membership. Do not switch to `az`.
- **First restore needs feed auth.** A 401 on first start = missing/expired Azure
  Artifacts Credential Provider token, not a broken server. Prime it with the
  step-1 command (`--interactive` seeds the token). To force re-auth after an
  expired token or account switch, delete the cache
  (`%LOCALAPPDATA%\MicrosoftCredentialProvider\SessionTokenCache.dat`) and
  restore once with `--interactive`. The plugin itself lives under
  `%USERPROFILE%\.nuget\plugins\{netcore,netfx}\CredentialProvider.Microsoft\`.
  Note this is the **`dnx` feed** provider — unrelated to the `<project>-ado`
  npm/Microsoft-account auth above.
- **`lion-repository`: never call its tools in parallel.** The server shares one
  DB connection; concurrent calls leak an open `DataReader` and poison the
  connection ("There is already an open DataReader…") until the process is
  restarted. Always call it sequentially.
- **`lion-repository` generic error on a write/create** (e.g. `create_object`)
  usually means a **stale server** with bad cached connection state, not a bad
  request. Restart the server (VS Code spawns a fresh `dnx` process).
- **`amt-config` data calls fail generically when the IIS backend is down.**
  `server_info` still works (it is static). Check the ControlCenter app pool in
  IIS before assuming the MCP itself is broken.
- **`net-debug` is Windows-only at runtime** even though its package targets
  `net10.0`.

## Re-run when

- A new engineer sets up the machine (install the credential provider, prime the
  feed).
- MCP tools stop appearing or a server won't start (check feed auth, then the
  server's Output).
- A new server version is published to `AMT_Mcp` and you want it — reload the
  server so `dnx` pulls the latest.
