# Refine Project Memory

`continuity.md` is the shared, committed team brain. It grows every time someone
learns something durable — so it must be **curated**, or it outgrows the context
budget and the "loads every session" benefit erodes. This skill runs that
curation as a reviewed, non-destructive ritual.

Three jobs, one pass: **archive** what's done, **promote** what's generic into
skills, **shrink** what's verbose — leaving a lean file of current one-line facts.

## Step 0 — Locate memory and skills

1. Read `amity.project.json` -> `memory.shared` (path to `continuity.md`) and
   `sharedAmity` (the `amt-go-net` folder).
2. Identify both skills folders: the **project** one
   (`<Project>_Migration/.github/skills/`) and the **generic** one
   (`amt-go-net/.github/skills/`).
3. Read `continuity.md` in full.

## Step 1 — Classify every fact and Open Thread

Tag each fact with exactly one disposition:

| Disposition | When | Action |
|---|---|---|
| **KEEP** | durable, current, project-specific, already ~one line | leave as-is |
| **ARCHIVE** | issue solved / element no longer matters / superseded | move to `memory/archive/`, remove from `continuity.md` |
| **PROMOTE** | describes a repeatable **procedure** or a **recurring pattern** a skill should own | create/update a skill (Step 2), replace fact with a one-line pointer |
| **SHRINK** | durable but verbose (multi-paragraph) | move detail to `memory/tickets/<id>.md`, keep a one-line pointer |
| **DEDUPE** | overlaps another fact | merge into a single bullet |

Sweep **Open Threads**: any checked (`- [x]`) or obsolete item → archive/remove.

## Step 2 — Promote generic findings into skills (uses author-amity-skill)

For each **PROMOTE** fact:
1. Apply the placement rule from the `author-amity-skill` skill: generic
   procedure -> `amt-go-net`; names a customer app/screen/DB/ADO project ->
   `<Project>_Migration`.
2. **Prefer updating an existing skill** (add a step or a "Common pitfalls"
   entry) over creating a new one. Create a new skill only when no existing one
   fits.
3. Replace the `continuity.md` fact with a one-line pointer, e.g.
   *"Generator emits AmtVariable for native-int copy params — captured in skill
   `debug-transaction-server` (pitfalls)."* — or remove it entirely if fully
   captured.

This is the loop that turns accumulated findings into reusable capability: an
experienced engineer's finding becomes a skill every junior gets automatically.

## Step 3 — Archive, never delete

- Move faded facts to `memory/archive/<YYYY-Qn>.md` (create the file if missing),
  carrying their metadata footer. Keep an optional `memory/archive/INDEX.md`
  one-line-per-fact index.
- For a **superseded** fact, link old -> new instead of deleting.
- Preserve history: the fact's content is never hard-deleted — git history plus
  the archive are the record. A fact lives in exactly one place (continuity
  **or** archive).

## Step 4 — Keep it lean

- Target state: `continuity.md` holds only **current, one-line facts** grouped in
  its existing sections (Architectural Invariants / Key Decisions / Defect
  Findings / Open Threads). Heavy detail lives in `memory/tickets/` or in skills.
- Merge overlapping bullets; keep one footer per fact.

## Step 5 — Review gate (REQUIRED — do not skip)

1. Present a **plan first** as a summary table: what will be KEPT / ARCHIVED /
   PROMOTED (which skill created or updated) / SHRUNK / DEDUPED, and which Open
   Threads are swept.
2. Get the user's approval.
3. Apply the edits: update `continuity.md`, write archive/ticket files, and
   create/update the skills.
4. Commit as one reviewed change set (memory edits + new/updated skills
   together). **Never `git push`** unless the user asks in that message.

## Output

A short report:
- `KEEP: n · ARCHIVE: n · PROMOTE: n · SHRINK: n · DEDUPE: n · threads swept: n`
- New/updated skills with their paths and layer (generic vs project).
- Archive file(s) written.

## Guardrails

- **Never hard-delete a fact** — archive it.
- **Never invent facts** — only reorganize/relocate what already exists.
- **Never leak secrets/PII** into the archive (there should be none to begin with).
- **Always show the plan before writing**; this is a curation ritual, not an
  autonomous rewrite.
- One fact, one place. Draft -> review -> commit. No push.
