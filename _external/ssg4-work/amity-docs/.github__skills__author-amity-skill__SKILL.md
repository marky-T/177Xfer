# Author an AMITY Skill

## What an AMITY skill IS

> **AMITY skill = a generic skill (the procedure / the "how") + project
> configuration (the data / the "which").**

A *generic skill* on its own is reusable but abstract. It becomes an *AMITY
skill* for a project when that project supplies the configuration it needs
(application names, transaction-server names, DB names, ports, paths). The
generic procedure lives in `amt-go-net`; the configuration lives in the
project repo's `amity.project.json`. Improve the procedure once → every project
benefits. Add a new app → change only the project config → zero skill edits.

## Two layers

| Layer | Repo | Holds |
|---|---|---|
| **Generic / platform** | `amt-go-net/.github/skills/` | procedures true for *any* AMT (.NET or Java) migration |
| **Project / engagement** | `<Project>_Migration/.github/skills/` | skills that name a specific customer's apps/screens/DBs/ADO project |

## The placement rule (apply to the skill BODY, not the topic)

> If you could hand the skill to a **different .NET/Java-AMT team unchanged**, it
> is **generic** → `amt-go-net`. If it names a **customer app, transaction code,
> screen number, DB name, or ADO project**, it is **project-specific** →
> `<Project>_Migration`.

| Signal in the skill body | Layer / repo |
|---|---|
| AMT tool mechanics (converter, generator, Lion repo, transaction server, IIS, Keycloak) | generic → `amt-go-net` |
| Source→target conversion procedure, coding standards, build order | generic → `amt-go-net` |
| Names `AFBUS`, `UPRD-SRC-TXN001`, screen `1004`, DB `AFLINC`, ADO project `Federale` | project → `<Project>_Migration` |

## The three kinds of skill

| Kind | Where | Reads a profile? | Example |
|---|---|---|---|
| `pure-generic` | `amt-go-net` | no | `install-amt-mcp-servers`, `author-amity-skill` |
| `skill-with-profile` | `amt-go-net` (procedure) + project profile (data) | **yes** — from `amity.project.json` | `debug-transaction-server` |
| `pure-project` | `<Project>_Migration` | self-contained (data is inline) | `cobol-generator-error-analysis` |

**Prefer `skill-with-profile` over `pure-project`** whenever the *procedure* is
generic and only the *values* differ. Forking a whole skill per project is how
instruction drift starts.

## SKILL.md frontmatter convention

```yaml
---
name: <kebab-name>
layer: generic | project
kind: pure-generic | skill-with-profile | pure-project
requires: [<mcp-capability>, ...]     # optional; MCP capabilities the skill needs
profile: amity.project.json#/<json/pointer>   # only for skill-with-profile
description: >-
  One paragraph. State WHAT it does, then "USE WHEN ..." triggers and
  "DO NOT USE FOR ..." exclusions so the model selects it correctly.
---
```

- `requires` lets a skill degrade gracefully: on a `java` capabilityProfile the
  `net-debug` server is disabled, so a skill requiring it should say "use the
  Java debugger instead" rather than fail.
- `profile` is a JSON pointer into the project manifest so the skill knows
  exactly where its data lives.

## Creating a `skill-with-profile` (the important pattern)

1. **Write the procedure** in `amt-go-net/.github/skills/<name>/SKILL.md`.
   Parameterize every project-specific value. Add a **Step 0 — Resolve the
   target from the project profile (REQUIRED FIRST)** that reads the values.
2. **Declare the data shape** in the project manifest. Add/extend a block in
   `<Project>_Migration/amity.project.json`, e.g.:

   ```jsonc
   "runtime": {
     "applications": [
       { "name": "AFBUS_AMT", "transactionServer": "<name>",
         "debugPort": 5005, "sysIni": "Settings/sys.ini",
         "controllerPool": "Working_ControlCenterBLPool" }
     ]
   }
   ```
3. **Point the skill at it** via the `profile:` frontmatter key (JSON pointer).
4. **Never hard-code** a project value in the generic skill. If the profile entry
   is missing, the skill asks the user and offers to add it.

## MCP capability profile

Each project declares its target-language capability in `amity.project.json ->
mcp.capabilityProfile` (`dotnet` or `java`) and a `servers{}` enable map.
`dotnet` enables `net-debug`; `java` disables it (no .NET debugger) while keeping
converter/generator/`lion-repository`/`amt-config`/`amt-script`. A skill's
`requires:` list is checked against that map.

## Promotion path (project → generic)

When a **second** project needs a `pure-project` skill:

1. Copy it to `amt-go-net/.github/skills/`.
2. Replace every hard-coded customer value with a profile read; change `kind` to
   `skill-with-profile` and add the `profile:` pointer.
3. Add the data block to **each** consuming project's `amity.project.json`.
4. Delete the original from the project repo (or leave a thin note pointing to
   the generic one).

## Authoring checklist

- [ ] Placement rule applied to the **body** (generic vs project).
- [ ] `kind` chosen; `skill-with-profile` used instead of a fork when only data differs.
- [ ] Frontmatter has `name`, `layer`, `kind`, a strong `description` with
      USE WHEN / DO NOT USE FOR, and `requires`/`profile` where relevant.
- [ ] No project-specific literal in a generic skill.
- [ ] Profile block added to the project manifest for every `skill-with-profile`.
- [ ] `requires` matches the project's `mcp.capabilityProfile`.
- [ ] Committed as reviewed changes (skills are code — PR + review).
