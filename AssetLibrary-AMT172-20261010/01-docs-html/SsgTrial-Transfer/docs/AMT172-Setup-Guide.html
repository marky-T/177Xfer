Starting an Already-Setup AMT Environment After Reboot

Use this after a machine reboot when SQL Server, IIS, and the AMT install are already configured — Keycloak and the AMT services just need to be brought back up.

AStart Keycloak ▼
powershell
$env:JAVA_HOME = "C:\Program Files\Microsoft\jdk-21.0.11.10-hotspot"
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
Set-Location "C:\Keycloak\keycloak-26.2.5\bin"
Start-Process "cmd.exe" -ArgumentList "/c kc.bat start-dev --http-port 8080 > C:\Keycloak\keycloak.log 2>&1" -WindowStyle Minimized
Write-Host "Waiting for Keycloak on port 8080..."
for ($i = 1; $i -le 24; $i++) {
    Start-Sleep -Seconds 5
    $up = (Test-NetConnection localhost -Port 8080 -WarningAction SilentlyContinue).TcpTestSucceeded
    if ($up) { Write-Host "Keycloak UP at $($i*5)s"; break }
    Write-Host "  $($i*5)s..."
}

Expected console output: Keycloak UP at <n>s (typically ~20s)

BOpen Control Center and sign in ▼

Navigate to AMT Control Center Web Application.

You will be redirected to the Keycloak sign-in page (localhost:8080/realms/master/...). Enter your AMT username and password, then click Sign In.

Step 12.6 — Verify PROGRAM-ID Matches Object Name in .LionSource

CobolConverterConsole.exe derives the object name from the SSG filename (e.g. ASSURFED_UTILIT_MONTANT_SIGNE(P)). After suffix-stripping, the stored name becomes ASSURFED_UTILIT_MONTANT_SIGNE, but the COBOL source body contains PROGRAM-ID. MONTANT. — a completely different identifier. Check before importing: open the .LionSource file in a text editor:

  • Find <OBJECT=…,COBOL PROGRAM> — the value between = and , is the stored object name
  • Find Name= in the <REVSET=…> block — same value
  • Find PROGRAM-ID. in the <DATA=Code> block — this is what the generator uses
  • All three should match after stripping any (P) / (F) / (S) suffix

$f = "C:\Amt\Migration\CobolConvert\output\my-source.LionSource"

  4. Read a record. The runtime reads exactly [INPUT,1,1,2] = 80 characters into the working-storage buffer WS-IN. If there are no more lines, it jumps to step 8.
  5. Copy to output buffer. The entire 80 characters are copied byte-for-byte into WS-OUT. At this point the output is an exact clone of the input.

  8. Close files and exit. Both files are closed, the job row in the database is updated to “Done”, and the process exits with code 0.

TRI_ASCII (Sort-Fichout-1) SSG/ECL Purpose

TRI_ASCII is a reusable sort utility, not a fixed program. The COBOL source contains no literal file names, record sizes, or key positions — every one of those is an SSG/ECL parameter substituted at compile time. The same source file generates a different sort program for each calling ECL job: one job might sort a 120-byte ledger file on an 8-byte account key at offset 10; another might sort a 200-byte claims file on a 12-byte reference at offset 0; the trial here uses 80-byte records with an 8-byte key at offset 0. T_SORT is essential precisely because the key position cannot be hardcoded — it is always whatever the ECL job says: keyOffset = [KEYS,1,COL,1] bytes of filler before the key, keyWidth = [KEYS,1,COL,2] bytes for the key itself (e.g. offset 0 + width 8 for the trial; offset 10 + width 12 for a different job). The *DEFINE FILLADD macro in the SSG source expresses this filler logic — it is suppressed by Remove-SsgDirectives.ps1 and re-expressed in C# as if (keyOffset > 0) { new AmtVarAlpha(keyOffset, m_Sort_R1); }. The file names FICHIN-1 and FICHOUT-1 in the default fields are only a placeholder for the current ECL stub — they will be set from the actual ECL parameters in a production run.

Sort-Fichout-1 Run Review

What actually happens when the program executes — in plain terms. SSG tag annotations show where each SSG macro construct is in effect.

  1. Start-up. The AMT runtime reads sys.ini, connects to the SQL Server databases, and creates a job row so the run is tracked.
  2. Open input file. The runtime locates FICHIN-1.DAT in the Extracts folder and opens it for sequential reading. The file name comes from the SSG parameter [INPUT,1,A,1] (T4), now stored in m_FichinName and passed to SetOptions() instead of being a hardcoded literal. The record size — 80 characters — comes from [INPUT,1,A,2] (T3), passed as m_RecordSizeIn=80 into Fd_Rec_In_1.
  3. Open sort work file. A temporary file (SORT-FICHOUT-1_SORTFILE<requestId>) is created to hold records during sorting. Its layout is defined by two classes working together: Fd_Sort_Rec (the flat 80-byte record, driven by [OUTPUT,1,1,2] T3 = m_RecordSizeOut) and Fd_Sort_R1 which redefines it with the sort key overlay: optional filler of [KEYS,1,COL,1] (T_SORT = keyOffset=0, so no filler here) then Sort_Key_1 of width [KEYS,1,COL,2] (T_SORT = keyWidth=8). The *DEFINE FILLADD macro in the SSG source expressed this filler logic; it is now in C# as if (keyOffset > 0) { new AmtVarAlpha(keyOffset, m_Sort_R1); }.
  4. Stage records for sort (Inp loop). Each record from TAPE-1 is copied verbatim into the sort work file. This is the COBOL SORT â€¦ INPUT PROCEDURE section.
  5. Sort. SortFiles(Sortfile, new Tuple<AmtVariable, AmtOrder>[] { Tuple.Create((AmtVariable)m_Fd_Sort_R1.Sort_Key_1, AmtOrder.Ascending) }, false) is called. The runtime sorts all staged records by the 8-byte key at offset 0, ascending (standard ASCII collation). The sort key field was constructed using the T_SORT parameters — if keyOffset had been non-zero, a filler entry would have preceded it in the m_Sort_R1 structure, shifting the key to the correct byte position.
  6. Write sorted output (Outp loop). The sort work file is re-opened for sequential reading. Each sorted record is copied into TAPEOUT (FICHOUT-1.DAT), whose file name comes from [OUTPUT,1,1,1] (T4) — stored in m_FichouName — and whose record size is [OUTPUT,1,1,2] (T3) = 80 bytes.
  7. Close files, display counts, exit. Both files are closed. The program displays input and output record counts UPON PRINTER (written to the Prints folder when the Application Server is available). The sort work file is purged. The process exits with code 0.
